ELF 段（Section）完整学习笔记

本文档以 readelf -S libcompile_learn.so 的输出为线索，系统梳理 ELF 二进制文件中各段（Section）的底层原理、数据结构与运行时行为。全文按照 “从元信息到代码数据，从静态链接到动态运行，从异常处理到调试信息” 的逻辑链路重新编排，并在关键节点补充编译期与运行期的深度剖析。

一、ELF 文件基础与元信息段

[0] NULL 段（哨兵段）

NULL 段是所有 ELF 文件的 ==零号锚点==，其索引号为 0，所有字段被刻意清零。

设计意图：

维度 说明
哨兵语义 sh_type == SHT_NULL 在所有条件判断中天然为假，作为”无段”的有效返回值
边界安全 防止索引越界——任何对 sections[0] 的访问都不会产生未定义行为
溢出收容 当段数量超过 ELF 头部 e_shnum 字段的编码上限时，扩展计数会被存入 NULL 段的 sh_size 与 sh_link 字段

==NULL 段并非”空无一物”，而是 ELF 格式设计中的防御性编程典范。==

[29] .comment — 工具链指纹段

.comment 存储一串 ASCII 字符串，记录了生成该二进制文件的完整工具链信息：

  • 编译器版本：如 GCC: (GNU) 12.2.0
  • 编译选项：部分关键编译标志
  • 工具标识：若使用 Clang、ICC 等非 GCC 编译器，此处会留下对应的厂商指纹

用途：

  1. 版本审计：在排查 ABI 不兼容导致的诡异崩溃时，通过 .comment 可快速确认构建所用的编译器版本
  2. 版权声明：某些专有软件会在此写入版权标识

.comment 段在运行时完全不被需要，可以通过 strip 命令安全删除以缩减二进制体积。

[31] .shstrtab — 段名字符串表

核心问题：用 readelf -S 看到的人类可读段名（如 .text、.data）并非直接存储在段头部结构体中。

原因：段名长度不定，若将字符串直接嵌入 Elf64_Shdr 结构体，会破坏其固定大小（64 字节），导致无法通过数组下标进行 $O(1)$ 索引。

解决方案：

  • .shstrtab 将所有段的名字以 \0 分隔连续堆叠存储
  • 每个 Elf64_Shdr 中仅保存一个 sh_name 字段（整型偏移量），指向 .shstrtab 中的对应位置

==固定长度结构体 + 变长数据集中存储 == 是二进制格式设计中的通用模式，.dynstr 与 .strtab 采用了相同策略。==

[32] .interp — 动态链接器路径段

.interp 存储动态链接器的绝对路径（如 /lib64/ld-linux-x86-64.so.2）。

运行时行为：

==.interp 的存在标记了该 ELF 是”动态链接可执行文件”。若缺失且引用了外部符号，内核将直接拒绝加载。==

二、Note 段：安全、身份与兼容性元数据

[1] .note.gnu.property — CPU 安全特性声明段

这是现代 Linux 系统（尤其是启用了 Intel/AMD 硬件级安全保护时）至关重要的 ==安全体检报告段==。

背景：现代 CPU（Intel 第 11 代起、AMD 对应代际）引入了 **CET (Control-flow Enforcement Technology，控制流强制技术)**，专门防御 ROP（返回导向编程）和 COP/JOP（跳转导向编程）攻击。

存储内容：该段以二进制位（Bit）编码以下信息：

“本共享库在编译时已完整支持 IBT（间接跳转追踪） 与 SHSTK（影子栈） 硬件防御，请内核与动态链接器放心开启硬件加速拦截。”

==CET 是通过硬件 + 编译器 + 内核三方协同实现的纵深防御体系。.note.gnu.property 是编译器的”承诺书”，告知系统该二进制已具备相应的代码形态（如所有间接跳转目标均以 ENDBR64 开头）。==

[2] .note.gnu.build-id — 二进制数字身份证

该段存储全球唯一的 ==二进制指纹==。

生成过程：

应用场景：

[39] .note.ABI-tag — ABI 兼容性标签

记录该二进制文件遵循的 ABI 规范版本信息，供动态链接器在加载时进行兼容性校验。

三、动态链接核心基础设施

[21] .dynamic — 动态配置清单

若将 ELF 二进制比作一份说明书，.dynamic 就是其中的 ==动态配置清单==——仅在程序加载到内存时，由动态链接器读取解析。

数据结构：.dynamic 段由一系列 Elf64_Dyn 结构体组成，每个结构体是一个键值对：

键 (d_tag) 含义
DT_NEEDED 依赖的共享库名称（如 libc.so.6）
DT_RPATH / DT_RUNPATH 共享库搜索路径
DT_SONAME 本库自身的规范名称
DT_INIT / DT_FINI 初始化与清理函数地址
DT_SYMTAB / DT_STRTAB 动态符号表及其字符串表地址
DT_PLTGOT .got.plt 段的地址

运行时加载流程：

与 Conda 的关系：Conda 构建工具扫描包内所有二进制的 .dynamic 段，若发现其依赖了错误的系统库路径，则通过 patchelf 工具修改 DT_RPATH，使其指向 Conda 环境内的隔离路径。

[4] .dynsym — 动态符号表

.dynsym 是 ==给操作系统和动态链接器看的符号表==。它是完整符号表 .symtab 的严格子集，仅保留需要跨越库边界的符号：

  • 导出符号：本库暴露给其他模块使用的函数/变量
  • 导入符号：本库引用的外部函数/变量

关键属性：

条目结构：在 64 位系统上，每个 Elf64_Sym 结构体被严格固定为 24 字节，包含：

字段 大小 含义
st_name 4 字节 符号名在 .dynstr 中的偏移量
st_info 1 字节 符号类型与绑定属性
st_other 1 字节 可见性 (Visibility)
st_shndx 2 字节 所在段的索引
st_value 8 字节 符号地址或偏移量
st_size 8 字节 符号占用字节数

[5] .dynstr — 动态字符串表

设计动机：Elf64_Sym 固定 24 字节，st_name 仅 4 字节，无法容纳任意长度的符号名。实际上，st_name 并非名字本身，而是一个 ==指向 .dynstr 的偏移量（坐标）==。

存储模型：

==固定长度记录 + 变长数据池，这是 .symtab/.strtab 以及 .shstrtab 共同遵循的设计范式。==

[3] .gnu.hash — GNU 哈希加速索引

在现代 ELF 动态链接体系中，.gnu.hash 是为 .dynsym 配备的 ==高性能哈希索引表==。

问题场景：中型程序加载 50 个 .so，总计 10 万个导出符号。若动态链接器对每个未解析的外部符号都遍历这 10 万个符号做 strcmp，启动延迟将不可接受。

解决方案：将查找时间从 $O(N)$ 降至 $O(1)$。

.gnu.hash 使用 Bloom Filter 进行快速否定（立即排除不存在的符号），再通过哈希桶进行精确匹配，极大加速了动态链接的符号解析过程。

这是 Linux 为解决 ==动态库升级导致老程序崩溃== 而设计的 符号版本控制机制 的物理载体。

四、重定位：从相对坐标到绝对地址

[8] .rela.dyn — 数据段重定位表

在动态链接的共享库中，同一个 .so 文件在不同进程里可能被加载到不同的虚拟内存基地址（Base Address）。

核心矛盾：

  • .text（代码段）是只读的 → 不能事后修改指令中的地址
  • 但全局数据和全局指针必须在加载时知道绝对地址

解决方案：.rela.dyn 是 ==动态链接器用来将”相对地图”转化为”绝对坐标”的最后一把钥匙==。

与 .rela.plt 的关键区别：

特性 .rela.dyn .rela.plt
作用对象 全局变量、数据指针、vtable 等 外部函数调用
解析时机 加载时（Load Time）一次性全部解析 延迟绑定（Lazy Binding），首次调用时才解析
目标段 .got（.data 相关条目） .got.plt
是否可延迟 否，必须在 main() 之前完成 是，通过 PLT 桩代码按需触发

[9] .rela.plt — 函数延迟绑定重定位表

.rela.plt 实现了动态链接的另一核心神技：==延迟绑定（Lazy Binding）==。

问题分析：

延迟绑定策略：==<U+201C>不到万不得已，绝不查地址。<U+201D>==

五、PLT 家族：过程链接的三层跳板

[10] .plt — 过程链接表

在现代动态链接机制（尤其是开启 PIC 位置无关代码后），==代码段是只读的==，不能在 .text 中直接写入函数的目标绝对地址。

.plt 的定位：代码段中的 ==一小段跳板代码==，作为从”相对调用”到”绝对地址”的桥梁。

PLT 条目的两阶段行为：

阶段 .got.plt 内容 .plt 行为
首次调用前 指向 PLT 解析桩的地址 压入符号索引 → 跳转公共解析器 → 查找真实地址 → 回填 .got.plt
首次调用后 目标函数的真实地址 直接 jmp *(%rip + offset) → 单指令开销

[11] .plt.got — 优化版快速跳板

.plt.got 是 .plt 的变体，为 x86_64 架构专门优化。

与标准 .plt 的差异：

特性 .plt .plt.got
功能定位 处理首次调用 + 后续调用 仅处理 ==已解析地址后的快速跳转==
典型指令数 多条（含 push 索引 + jmp 解析器） 极少（通常仅一条 jmp 指令）
核心指令 push $index → jmp resolver jmp QWORD PTR [rip + offset]

[12] .plt.sec — 安全 PLT

.plt.sec 是为适配现代处理器 ==执行流完整性（CET）== 检查而设计的 PLT 变体。

设计动机：

传统 .plt 中混杂了跳转逻辑与辅助查找逻辑。.plt.sec 将其剥离为两个独立段：

段 职责 内存权限
.plt 保留最基础的跳转辅助逻辑（兼容旧链接器） RX（可读可执行）
.plt.sec ==真正的跳转目的地==，执行核心跳转指令 可以更细粒度地控制内存保护属性（如设为只读）

调用链路：

.plt.sec 将跳转目标进行精确对齐，使现代 CPU 的间接跳转追踪（IBT）能够验证目标指令为 ENDBR64，防止黑客利用跳转到指令中间位置的攻击手法。

六、代码与数据段

[16] .text — 代码段

.text 是存放所有编译后的 ==机器指令== 的只读段。

核心属性：

属性 说明
内存权限 R-X（只读 + 可执行）
物理内存共享 同一 .so 的 .text 被所有进程共享同一物理页，不浪费一个字节
寻址方式 全部采用 ==RIP 相对寻址==，禁止包含绝对地址

为何不能包含绝对地址？

==-fPIC（位置无关代码）是现代 Linux 系统的默认选项，它强制 .text 中所有寻址均为相对寻址。==

名称由来：源于早期 Unix 汇编器设计，代码被视为 “Text”，数据被视为 “Data”，即便如今存放的是二进制机器码，名称仍然沿用。

[17] .rodata — 只读数据段

存放所有编译期确定且不可变的数据：

内容类型 示例
字符串常量 printf("Hello, World!") 中的 "Hello, World!"
const 常量 const int g_version = 2026;
数组/结构体常量 const int table[] = {1, 2, 3, 4};
==C++ 虚函数表 (vtable)== 类的虚函数指针数组

vtable 为何放在 .rodata？

字符串合并优化：编译器开启”字符串合并”功能后，若代码中出现三次 const char* s = "Error";，链接器仅向 .rodata 存放一个 "Error"，所有指针指向同一内存地址。

[24] .data — 已初始化数据段

存放已显式初始化为非零值的全局变量与静态变量。

[25] .bss — 零初始化数据段

==.bss 在磁盘上的二进制文件中不占用实际物理存储空间。==

存储策略：

三段对比总结：

段名 变量类型 初始化内容 磁盘占用 内存权限
.data 全局/静态 非零初值 有 读写
.bss 全局/静态 零 / 未初始化 ==无== 读写（初始化为 0）

[43] .tdata — 线程局部已初始化数据段

存放已初始化的 ==线程局部变量（TLS）==。每个线程拥有独立副本。

[44] .tbss — 线程局部零初始化数据段

存放未初始化的线程局部变量，与 .bss 策略类似——磁盘不占用空间，运行时零填充。

七、初始化与清理段

[13] .init — 前置初始化代码段

在 ELF 的世界里，==程序的起点不是 main()，终点也不是 return 0==。

.init 的作用：在 main() 执行之前，自动运行初始化代码。

触发条件（编译器自动生成）：

  • 全局变量初始化
  • 静态对象构造（C++）
  • __attribute__((constructor)) 修饰的函数

执行者：动态链接器 ld.so。它在完成所有重定位工作（.rela.dyn）、填好函数地址（.got.plt）之后，==跳入 .init 段逐条执行其中的代码==，最后才将控制权交给 main()。

[14] .fini — 后置清理代码段

与 .init 对应，.fini 存放程序在 exit() 或 return 之后自动运行的清理代码。

用途：释放全局内存、关闭文件句柄、清理互斥锁。

执行时机：进程即将退出、但从内存中彻底移除之前。

[15] .init_array 与 .fini_array — 现代化初始化机制

现代 ELF 文件中更常见的是 .init_array 和 .fini_array，而非原始的 .init/.fini 代码段。

关键区别：

特性 .init / .fini .init_array / .fini_array
内容形态 ==纯粹的机器码指令== ==函数指针数组==
执行方式 直接跳入段内逐条执行 遍历数组，依次 call 每个函数指针
灵活性 编译器生成的单一代码快照 允许多个源文件各自注册构造/析构函数

实现原理：

==这些”在 main 之前或之后自动执行的逻辑”并非凭空产生，而是编译器和链接器协同”缝合”进 ELF 结构中的。==

八、异常处理与栈回溯段

[18] .eh_frame_hdr — 异常帧头部索引

.eh_frame_hdr 是为实现 ==快速索引== 而存在的查找表，其本质是经过排序的二分搜索目录。

问题分析：

.eh_frame 记录的是”如何从任一指令位置还原调用栈”的规则。但其原始排列顺序遵循编译器的编译顺序（逐个翻译单元），在链接后呈现 ==本质上随性甚至混乱的顺序==。

当异常发生时，CPU 需要立即根据当前 RIP 查找对应的异常处理规则。若在无序的 .eh_frame 中线性扫描，性能不可接受。

解决方案：

[19] .eh_frame — 异常帧信息

.eh_frame 的核心作用是实现 ==栈回溯（Stack Unwinding）==。

当程序发生异常（throw）或需要堆栈追踪（如 GDB 打印调用栈）时，系统必须回答三个问题：

  1. ==当前的函数调用链路是怎样的？==（谁调用了我？我调用了谁？）
  2. ==上一级函数的栈帧在哪？==（寄存器状态、返回地址在哪？）
  3. ==当前函数有哪些局部对象需要清理？==（析构函数在哪？）

内部表示：.eh_frame 存储一组 CFI (Call Frame Information) 指令：

指令 含义
DW_CFA_advance_loc 指示代码偏移量
DW_CFA_def_cfa_offset 指示栈指针的变化量
DW_CFA_offset 指示某个寄存器的值保存在栈的哪个位置

这些指令被高度压缩编码，即使程序代码量巨大，.eh_frame 的物理占用也保持可控。

[20] .gcc_except_table — 语言特定数据区 (LSDA)

若说 .eh_frame 负责回答 ==怎么回溯==（栈帧撤销、寄存器恢复），那么 .gcc_except_table 负责回答：

  • ==在何处停止回溯==
  • ==如何匹配 catch 块==

记录内容：

信息 说明
try 块覆盖范围 代码段中哪些地址范围受 try 保护
异常类型信息 (Type Info) 用于与 catch (Type e) 进行 RTTI 比对
catch 块跳转地址 异常被抛出后，程序应该跳转到哪个 catch 块

九、全局偏移表 (GOT) 家族

[22] .got — 全局偏移表

现代操作系统启用 ASLR，程序加载位置不固定。因此 .text 中的指令 ==不能直接引用绝对地址==，但又必须访问共享库中的函数和全局变量。

.got 的定位：==一个数据段，专门存放外部函数和全局变量的绝对地址==。代码段通过间接寻址的方式先查 .got，再获取真实地址。

[23] .got.plt — 函数地址懒加载表

两个 GOT 段的职责划分：

段 存放内容 填充时机
.got 全局变量 / 数据地址 加载时一次性填入
.got.plt 函数地址（printf()、malloc() 等） ==懒加载——首次调用时才填入==

.got.plt 前三个特殊槽位：

槽位 内容 用途
槽位 0 _DYNAMIC 段的地址 让动态链接器定位整个 .dynamic 结构
槽位 1 link_map 数据结构地址 跟踪所有已加载的动态库
槽位 2 _dl_runtime_resolve 函数地址 ==幕后解析引擎——负责查找真实函数地址并回填==

[48] Full RELRO 下的 .got.plt

在开启了 Full RELRO（Relocation Read-Only）保护的程序中：.got.plt 被合并入 .got，且整个段在重定位完成后被标记为 ==只读==。

安全收益：即使攻击者获得了任意地址写入的能力，也无法篡改已解析的函数指针（因为 .got 已被 mprotect 设为只读）。

代价：必须放弃延迟绑定——所有外部函数在 main() 之前全部解析完毕。

十、符号表与字符串表

[30] .symtab — 完整符号表

若说 .got 和 .dynamic 是运行时的导航图，那么 .symtab 就是这份导航图背后的 ==原始定义库==。

对比：

特性 .symtab .dynsym
包含范围 所有符号（含内部函数、局部静态变量、调试符号） 仅动态链接所需的最小集合
运行时需求 ==不需要==（strip 后程序正常运行） ==必须保留==（否则无法启动）
主要用途 调试 (GDB)、静态链接、逆向工程 动态加载与符号解析
大小 较大 精简

每条符号记录包含：符号名、值（地址/偏移）、大小、类型（FUNC/OBJECT/SECTION）、绑定（GLOBAL/LOCAL）。

[30] .strtab — 字符串表

.strtab 是非常纯粹的辅助段——它是一连串以 \0 结尾的 C 风格字符串。

十一、调试信息段 (DWARF)

[33] .debug_aranges — 地址范围查找表

DWARF 调试信息的一部分，是为优化调试器查找效率而存在的 ==预建索引==。

问题：GDB 在某地址停下时，需要知道”这个地址属于哪个编译单元？”。若无索引，必须遍历所有编译单元的 .debug_info，解析其地址范围（DW_AT_low_pc ~ DW_AT_high_pc），在大型项目中极慢。

解决方案：.debug_aranges 将地址范围直接映射到编译单元偏移量，实现 $O(1)$ 或 $O(\log N)$ 查询。

存储内容：

字段 含义
Start Address 地址范围起始点
Length 范围长度
CU Offset 指向该地址范围所属 .debug_info 的具体偏移

[34] .debug_info — 核心调试信息

当 GDB 解析 .debug_info 时，能还原几乎所有原始代码信息：

  • 数据结构：类的成员数量、字节数、偏移量
  • 函数声明：函数名、返回值类型、参数列表及其类型
  • 源代码映射：变量定义的文件与行号

内部结构：.debug_info 以 DIE (Debugging Information Entry) 为单元形成树状结构。

每个 DIE 包含：

  • Tag：如 DW_TAG_compile_unit（编译单元）、DW_TAG_subprogram（函数）、DW_TAG_base_type（基本类型）
  • Attribute：如 DW_AT_name（名字）、DW_AT_type（类型引用）、DW_AT_location（变量存储位置）

与其他调试段的关系：

相关段 关系
.debug_str .debug_info 中的字符串不直接存放，而是存偏移量指向 .debug_str（==字符串去重==）
.debug_line .debug_info 告知函数位置，.debug_line 告知具体指令对应源码行号
.debug_abbrev ==最关键配对==：.debug_abbrev 预定义 DIE 结构模式并赋予编号，.debug_info 仅存编号，大幅压缩体积

[35] .debug_abbrev — 缩写表

设计动机：.debug_info 中的每个 DIE 都需要描述自身结构（如”我是函数，我有 Name、Line、Type 三个属性”）。若每个 DIE 完整重复描述，调试信息体积将爆炸。

解决方案：将常见的 DIE 结构模式预定义为编号（Abbrev Number），.debug_info 中仅存编号即可。

这是调试信息压缩的核心策略——==用查表替代重复描述==。

[36] .debug_line — 行号映射表

编译器在生成机器码时会进行大量优化（指令重排、函数内联、循环展开），导致：

  • 源代码第 10 行可能被拆散到不同的内存位置
  • 机器码中连续的两条指令可能分别来自源码第 10 行和第 50 行

.debug_line 记录 ==指令地址到源代码行号的映射==：

这是 GDB 实现”单步执行（next）”和行级断点的物理基础。

[37] .debug_str — 调试字符串表

在 .debug_info 和 .debug_abbrev 中会大量出现重复字符串（变量名、文件名、编译器标识）。若在每个 DIE 中完整存储，体积巨大。

.debug_str 将所有字符串统一存放，.debug_info 中仅存偏移量。

[38] .debug_line_str — 行号路径字符串表

为何不与 .debug_str 合并？

段 存储内容 读取特征
.debug_str 通用调试字符串（变量名、函数名、类型名、编译器版本） 分散访问
.debug_line_str ==文件路径字符串==（如 /home/user/project/src/main.c） 行号查找时高频集中读取

分离收益：

  • 调试器进行行号查找时，只需 mmap .debug_line_str，无需将庞大的 .debug_str 也加载进来
  • 利用内存映射（Memory Mapping）进行更好的缓存优化

在 DWARF 4 及以前，路径字符串直接存于 .debug_line 内部，导致冗余存储和解析复杂化。DWARF 5 引入 .debug_line_str 解决了这一问题。

十二、其他特殊段

[46] .gnu.lto — 链接时优化中间代码段

LTO (Link-Time Optimization) 产生的中间代码段，用于链接器在最后阶段进行 ==跨模块代码优化==。

.gnu.lto 存储的就是那些 ==GIMPLE 中间表示==，供链接器二次编译与全局优化。

[41] .rodata.cst16 / .rodata.str1.1 — 特殊只读段

编译器为特定对齐或合并策略生成的 .rodata 子变体，用于存放常量合并优化后的数据。

[42] .plt.got vs .plt.sec — 架构相关 PLT 变体

（已在前文第五部分详述。）

[45] .tdata1 — 扩展段

某些特殊编译器产生的 TLS 扩展段。

[40] .rel.dyn — .rela.dyn 的变体

.rel 与 .rela 的区别仅在于重定位条目中是否显式包含 Addend（加数）：

类型 Addend 位置
.rela.dyn (RELA) 显式存储于重定位条目中
.rel.dyn (REL) 隐式存储——Addend 藏在要被修补的内存位置上
