IPC 概述

IPC 是什么

IPC（Inter-Process Communication，进程间通信）是指操作系统中不同进程之间传输数据或交换信息的一套机制与技术。

在现代操作系统（如 Linux、Windows、macOS）中，出于安全和稳定性考虑，每个进程都拥有独立的虚拟内存空间。一个进程默认无法直接读取或修改另一个进程的内存数据。因此，当不同的进程需要协作完成任务时，就必须依靠 IPC 机制。

为什么需要 IPC

  1. 数据共享：多个用户或任务需要同时访问同一份数据。
  2. 模块化与解耦：将大型系统拆分为多个独立进程（如微服务架构、主进程 + 工作进程），提升系统的可扩展性和鲁棒性。
  3. 任务协作：一个进程的输出作为另一个进程的输入（例如 Unix 管道 cat file | grep "keyword"）。
  4. 资源隔离与安全：单个进程崩溃不会直接导致整个应用崩溃（如 Chrome 浏览器的多进程架构）。

常见 IPC 机制概览

IPC 机制 核心特点 适用场景
管道（Pipe / FIFO） 匿名管道用于父子进程；命名管道可用于任意进程。字节流，半双工。 简单线性数据流，如 shell 管道。
消息队列（Message Queue） 由操作系统维护的消息链表。消息天然具备边界，无需手动处理粘包。异步通信，解耦度高。 结构化消息传递，生产者-消费者模型。
共享内存（Shared Memory） 操作系统映射一段物理内存，使其同时被多个进程的虚拟地址空间挂载。==性能最高、速度最快的 IPC 方式==，因为数据无需在内核态与用户态之间频繁拷贝。 高频大数据量交换，如音视频流、数据库 Buffer Pool。
信号量与锁（Semaphore / Mutex） 主要控制并发访问的同步与互斥，通常配合共享内存使用。 临界区保护，资源计数。
信号（Signal） SIGINT、SIGKILL 等，主要用于异步通知，携带信息量极少。 进程控制、异常通知。
套接字（Socket） 支持跨网络通信，字节流（TCP）或数据报（UDP）。 网络服务、跨主机通信。

共享内存的核心原理

一句话总结

==不同的进程虚拟地址，映射到了相同的物理内存页（Physical Page Frames）。==

虚拟内存与页表背景

  1. 在现代操作系统中，进程使用的地址全部是 虚拟地址（Virtual Address），而不是物理内存的真实地址。每个进程都有自己独立的虚拟地址空间（例如 64 位系统下巨大的 0x0000000000000000 ~ 0x7FFFFFFFFFFF）。
  2. 操作系统（Linux 内核）通过 页表（Page Table） 建立”虚拟页”到”物理页框（Physical Page Frame）”的映射关系。CPU 中的 MMU（内存管理单元） 负责在运行时根据页表，把虚拟地址实时翻译成物理地址。
  3. 在普通情况下，进程 A 的虚拟页 $VA_1$ 映射到物理页 $PA_X$，进程 B 的虚拟页 $VA_2$ 映射到物理页 $PA_Y$。不同进程的物理页是隔离的，这就是操作系统的内存安全保护。

SHM 的核心机制：跨进程页表映射

POSIX SHM 突破了”内存隔离”。它的本质是让 Linux 内核的 MMU 将两个（或多个）不同进程的虚拟页，指向同一组物理内存页框。

==共享内存结构体里绝对不能存放绝对指针！== 进程 A 写入的指针地址（如 0x7ff010000000）在进程 B 的虚拟地址空间中毫无意义，解引用将导致段错误（Segmentation Fault）。必须使用相对偏移量（Offset）来引用共享内存块内部的数据。

通信方式 数据拷贝次数 涉及内核态切换

POSIX 共享内存 API 详解

Linux 下有两种实现共享内存的标准：POSIX 体系（现代推荐）和 System V 体系（传统老式）。本文只讨论 POSIX 体系。

共享内存的物理路径

在 Linux 系统下，POSIX 共享内存默认被挂载并映射到 Linux 的 tmpfs（临时内存文件系统）中。

真实物理路径：/dev/shm/

当你执行 shm_open("/my_shm_demo", ...) 后，系统会在 /dev/shm/ 目录下自动创建一个名为 my_shm_demo 的虚拟文件，即 /dev/shm/my_shm_demo。可以通过 ls /dev/shm/ 直接观察。

核心 API 流水线

整个共享内存的生命周期遵循严格的”创建 -> 调整大小 -> 映射 -> 使用 -> 解除映射 -> 销毁”流水线：

shm_open —— 创建或打开共享内存对象

参数解析：

参数 含义
name 共享内存对象的名称，必须以 / 开头（如 /my_shm_demo），长度不超过 NAME_MAX（通常 255 字符）。
oflag 打开标志位，支持按位或（`
mode 权限控制位（如 0666），仅在 O_CREAT 创建新对象时生效。

标志位详解：

标志 行为
O_CREAT 如果共享内存对象不存在，则新建；如果已存在，则直接打开现有对象。此时第三个参数 mode 才会生效。
O_RDWR 以可读可写方式打开。
O_RDONLY 以只读方式打开。
O_EXCL ==排它性创建==，必须与 O_CREAT 配合使用（O_CREAT | O_EXCL）。如果共享内存不存在则成功新建；如果已存在则 ==强制失败返回 -1==，同时将 errno 设置为 EEXIST。用于防止意外覆盖已有共享内存。
O_TRUNC 如果打开的共享内存对象已经存在，将其大小立即清空 / 截断为 0 字节。==可能导致其他正在使用该对象的进程崩溃==，需谨慎使用。

返回值： 成功返回文件描述符 fd；失败返回 -1，可通过 perror("shm_open") 打印错误原因。

ftruncate —— 设置共享内存大小

参数 含义
fd 已打开的文件描述符，即 shm_open() 的返回值。
length 目标字节大小（off_t 类型）。

为什么必须有这一步： 系统在 /dev/shm/ 临时内存文件系统中为你建立了一个条目，但它的默认初始大小是 0 字节。如果不调用 ftruncate 就执行 mmap，映射的内存大小为 0，后续读写将导致 SIGBUS 错误。

返回值： 成功返回 0；失败返回 -1 并设置 errno。

mmap —— 将共享内存映射到进程虚拟地址空间

这是整个 SHM 体系中最核心的系统调用，它把之前通过 shm_open 打开的共享内存区域（由文件描述符 fd 标识），直接 ==挂载 / 映射==到当前进程的虚拟地址空间中。

参数逐项拆解：

序号 参数 典型值 含义
1 addr NULL 指定映射到进程虚拟内存的起始首地址。传 NULL 表示让操作系统内核自动挑选一块最合适的虚拟内存地址，==这是最推荐、最安全的方式==。
2 length sizeof(SharedData) 要映射的内存区域大小（字节数）。
3 prot PROT_READ | PROT_WRITE Protection（内存保护属性）。指定当前进程对这块映射内存的读写权限。可选值：PROT_READ（可读）、PROT_WRITE（可写）、PROT_EXEC（可执行）、PROT_NONE（不可访问）。==注意：此处的权限不能超过 shm_open 时设置的权限==。
4 flags MAP_SHARED Map Flags（映射模式标记），极其关键。
5 fd fd File Descriptor，即 shm_open() 返回的那个整数 fd。
6 offset 0 文件偏移量，通常设为 0，表示从共享内存对象的起始位置开始映射。必须为页大小（通常 4096 字节）的整数倍。

Map Flags 详解：

Flag 含义
MAP_SHARED ==共享映射==。当前进程对这块内存的任何修改，会立刻对映射了同一共享内存的其他所有进程可见。修改会写回底层对象。
MAP_PRIVATE 私有映射（写时复制，Copy-on-Write）。修改对其他进程不可见，也不会写回底层对象。==不适用于 IPC 场景==。
MAP_ANONYMOUS 匿名映射：映射区域不对应磁盘上的文件，内存内容被自动初始化为全 0。此时 fd 参数必须为 -1，offset 必须为 0。适合父子进程间共享（fork 后子进程继承映射）。
MAP_LOCKED 将映射的内存物理页强行锁定在物理内存（RAM）中，防止被操作系统 Swap 交换到磁盘上（效果类似于 mlock()）。适合对实时性要求极高的系统。
MAP_HUGETLB 使用巨页（Huge Pages）进行映射。极大地减少硬件 TLB（页表缓存）Miss，显著提升超大内存访问（如 Redis、高性能 DPDK 网络处理）的吞吐量。

关键操作：用完立即 close(fd)

映射建立后，文件描述符 fd 的历史使命就已经完成。==应该立即调用 close(fd) 关闭文件描述符==，这不会影响已建立的映射关系，而且可以避免文件描述符泄漏。

munmap —— 解除内存映射

将之前通过 mmap 映射到进程虚拟地址空间的内存区域卸载。length 必须与 mmap 时指定的大小一致。

调用后，进程不能再访问该内存地址（否则触发 SIGSEGV），但不影响其他进程继续使用同一共享内存。

shm_unlink —— 销毁共享内存对象

从系统中删除指定名称的共享内存对象。类似于文件的 unlink：删除名字后，当前正在使用该对象的进程不受影响，但新进程无法再通过 shm_open 打开它。当最后一个进程 munmap 后，内核回收对应物理内存。

==在创建者进程中，通常先用 shm_unlink 清理可能残存的旧对象==（忽略返回值），再重新创建。

跨进程同步：使互斥锁在进程间生效

问题的根源

Linux 默认的 POSIX 互斥锁（pthread_mutex_t）只能在 同一个进程内的不同线程之间 生效。如果不特别处理，这把锁在跨进程使用时的行为是未定义的——可能完全无效，甚至直接引发崩溃。

原因：POSIX 互斥锁的默认属性是 **PTHREAD_PROCESS_PRIVATE**（进程私有的）。

解决方案：设置 PTHREAD_PROCESS_SHARED

==这是跨进程共享内存场景下使用 pthread_mutex_t 的必要步骤==，缺少此设置会导致未定义行为。

互斥锁的高级属性一览

除了 PTHREAD_PROCESS_SHARED 属性外，POSIX 互斥锁还支持以下类型（通过 pthread_mutexattr_settype 设置）：

锁类型 行为
普通锁（PTHREAD_MUTEX_NORMAL） 标准互斥锁。同一线程重复加锁会导致死锁。
检错锁（PTHREAD_MUTEX_ERRORCHECK） 同一线程重复 lock 不会卡死，而是返回 EDEADLK 错误码。==调试时非常好用==，可以快速发现重复加锁的 bug。
递归锁（PTHREAD_MUTEX_RECURSIVE） 可重入锁，允许同一个线程重复加锁（内部维护计数器）。但是加锁多少次就必须解锁多少次，计数器归零后才真正释放。
默认锁（PTHREAD_MUTEX_DEFAULT） 行为由实现定义，通常映射为普通锁。

此外还有健壮锁 / 非健壮锁（pthread_mutexattr_setrobust，用于处理持有锁的进程崩溃后锁的恢复）、优先级继承（PTHREAD_PRIO_INHERIT）、优先级天花板（PTHREAD_PRIO_PROTECT）等属性，适用于实时系统场景。

mutex 与 volatile 的隐含关系

==pthread_mutex_lock / pthread_mutex_unlock 自动充当了内存屏障（memory barrier）==，保证了互斥锁保护的临界区内对共享变量的修改，对其他线程 / 进程的可见性。因此，在正确加锁的场景下，不需要手动为共享数据添加 volatile 关键字。

小整数原子读

对于 int 或更小的整型（不超过 64 bit），在 x86_64 平台上对其的读操作天然是原子的，不会产生读取撕裂（Tearing）。但原子性不等于可见性——多核缓存一致性问题仍然存在，仍需锁或原子操作保障。

第一阶段：Creator 进程 —— 创建与初始化

编译期与运行期底层动作拆解

编译期：

  1. 编译器检查头文件 <fcntl.h>、<sys/mman.h> 中声明的函数签名，确保参数类型匹配。
  2. sizeof(SharedData) 在编译期计算为常量（如 48 字节），直接嵌入到 ftruncate 和 mmap 的调用参数中。
  3. O_CREAT | O_RDWR 等宏在预处理阶段展开为对应的整数常量。

运行期（按代码行序）：

  1. shm_unlink(SHM_NAME) —— 发起 unlink 系统调用，内核在 tmpfs 中删除 /dev/shm/my_shm_demo 的目录项。如果文件不存在，系统调用返回 -1（错误被忽略）。
  2. shm_open(SHM_NAME, O_CREAT | O_RDWR, 0666) —— 内核在 tmpfs 中创建一个新的共享内存文件 /dev/shm/my_shm_demo（初始大小为 0 字节），返回文件描述符 fd。该 fd 指向内核中一个 file 结构体，该结构体引用 tmpfs 中的一个 inode。
  3. ftruncate(fd, sizeof(SharedData)) —— 内核将 tmpfs 文件的 inode 大小从 0 扩展到 48 字节，并为其分配物理页框。
  4. mmap(NULL, ..., MAP_SHARED, fd, 0) —— 这是最关键的一步：
    • 内核在当前进程的虚拟地址空间中找一段 48 字节的空闲区域（返回起始地址给 data）。
    • 内核修改当前进程的页表，将这段虚拟地址映射到步骤 3 中分配的物理页框。
    • 因为指定了 MAP_SHARED，页表项被标记为共享映射。
  5. close(fd) —— 关闭文件描述符，释放进程 fd 表中的槽位。但因为页表中已建立映射，tmpfs inode 的引用计数不为 0，物理页框不会被释放。
  6. pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED) —— 设置互斥锁属性为跨进程共享。底层效果：初始化互斥锁时，锁的内部状态结构（futex 等）会被放置到共享内存区域而非进程私有堆中，使其他进程能够通过 futex 系统调用操作同一把锁。
  7. pthread_mutex_lock(&data->mutex) —— 如果锁空闲，直接获取；如果已被 Worker 持有，Creator 进入内核态通过 futex(FUTEX_WAIT) 挂起等待。pthread_mutex_unlock 通过 futex(FUTEX_WAKE) 唤醒等待者。

第二阶段：Worker 进程 —— 打开与协作

Worker 端运行期底层动作拆解

  1. shm_open(SHM_NAME, O_RDWR, 0666) —— 内核在 tmpfs 中查找 /dev/shm/my_shm_demo，找到已存在的 inode，返回一个新的 fd（该 fd 数字可能与 Creator 的不同，但底层引用了同一个 inode）。
  2. mmap(NULL, ..., MAP_SHARED, fd, 0) —— 内核再次执行页表修改操作：
    • 在 Worker 的虚拟地址空间中找一段 48 字节空闲区域（==地址可能和 Creator 端完全不同==，例如 Creator 映射到 0x7f0010000000 而 Worker 映射到 0x7f0020000000）。
    • 将 Worker 的虚拟页映射到与 Creator 相同的物理页框。
    • 此时两个进程的不同虚拟地址指向同一物理内存，实现零拷贝共享。
  3. close(fd) —— Worker 端关闭自己的文件描述符。
  4. Worker 和 Creator 通过 ==同一把== pthread_mutex_t（物理上在同一共享内存中）实现跨进程互斥。锁的内部状态（如 futex word）位于共享内存物理页框中，双方都能通过 futex 系统调用原子地读写。
  5. munmap 后 Worker 进程的对应虚拟地址区域被回收，页表项被清理。但物理页框仍在（Creator 或其他 Worker 还在映射）。

共享内存进阶话题

父子进程间无文件共享内存（MAP_ANONYMOUS）

在 fork 之前，父进程使用 mmap 配合 MAP_SHARED | MAP_ANONYMOUS 映射一块匿名共享内存。fork 后子进程自动继承这块映射，且因为标记为 MAP_SHARED，父子进程对这块内存的修改互相可见。

适用于简单的父子协作场景，无需 shm_open 创建具名对象。

环形缓冲区与零拷贝队列

共享内存本身只解决了”数据放在哪”的问题。生产环境通常需要在共享内存上构建 环形缓冲区（Ring Buffer / Circular Queue） 这种数据结构，才能高效地实现生产者-消费者模型。

这类数据结构的实现已超出共享内存 API 的范畴，属于数据结构设计的领域。核心挑战在于：如何用原子操作（CAS、FAA）替代互斥锁来实现无锁（Lock-Free）或多生产者-多消费者（MPMC）场景下的正确同步。

大模型与 GPU 场景下的巨页共享内存

在 GPU 计算和大模型推理 / 训练场景下，CPU 和 GPU 之间需要频繁传输海量数据。使用 HugePages（巨页） 可以显著降低 TLB Miss 率。

这需要系统预先配置巨页池（/proc/sys/vm/nr_hugepages）。

复杂无锁数据结构（Lock-Free Shared Memory）

当性能要求极高，连 pthread_mutex_lock 的开销（用户态 futex 操作，约 20-50ns）都无法接受时，需要实现无锁数据结构。常见的比如：

  • 无锁栈（Lock-Free Stack）：基于 CAS 的 Treiber Stack
  • 无锁队列（Lock-Free Queue）：基于 FAA + CAS 的 Michael-Scott Queue
  • 无锁哈希表

这些同样属于通用数据结构领域，与共享内存 API 本身关系不大，核心难点在于 内存序（Memory Order） 和 ABA 问题 的工程处理。

总结

POSIX 共享内存的学习曲线相对平缓。只要理解了操作系统的虚拟内存模型和页表映射机制，就能够掌握其核心原理。API 层面只有五个关键函数：shm_open、ftruncate、mmap、munmap、shm_unlink，流程清晰且高度正交。

真正的工程复杂度不在于 API 调用本身，而在于：

  1. 跨进程同步机制的正确配置（如 PTHREAD_PROCESS_SHARED）。
  2. 共享数据结构的设计（偏移量代替指针）。
  3. 具体业务场景下对性能与正确性的权衡（有锁 vs 无锁，普通页 vs 巨页）。

API 是简单的，工程实践是深邃的。
