0. 为什么需要 DWARF Unwind

上一篇的 Frame Pointer（FP）unwind 依赖一条 RBP 链：caller RBP = [RBP]、caller RIP = [RBP+8]。

但 FP 方法有它的软肋：只要编译器把 RBP 优化掉，整条链就断了。

具体地说，在开启优化、又没有加 -fno-omit-frame-pointer 的情况下，编译器会省略帧指针（-fomit-frame-pointer），
把 RBP 当成一个普通寄存器来用（省出一个寄存器，对代码调度更友好），
于是 [RBP] / [RBP+8] 就不再是「saved rbp / return addr」，FP unwind 就失效了。

这时候就需要 DWARF CFI：它不依赖任何固定的寄存器约定，而是由编译器在 ELF 里记下的一套「栈帧恢复规则」，
unwinder 照着规则就能把每一层 caller 的寄存器恢复出来。

1. DWARF 与 CFI 是什么

DWARF 是一种标准化的「调试信息格式」：编译器把程序的源码、机器码、函数、变量、栈帧等之间的对应关系记录到 ELF 文件里，
调试器和其他工具再利用这些信息理解机器码。

ELF 是整个目标文件 / 可执行文件的容器格式，而 DWARF 是其中用于描述调试信息的一套格式。
GCC 生成 ELF 文件的同时，会在里面加入 DWARF 相关的 section。

用 readelf -S test 通常能看到：.debug_info、.debug_abbrev、.debug_line、.debug_str 以及 .eh_frame 等。

2. CFI 的核心概念

2.1 CFA（Canonical Frame Address）

CFI 是编译器记录的一套「栈帧恢复规则」，告诉 unwinder：当程序执行到某个 IP 时，
怎样从当前寄存器状态恢复出 caller 的 RIP、RSP、RBP 等寄存器。

CFI 最重要的概念是 CFA（Canonical Frame Address，规范帧地址）：

CFA 定义为：在当前函数执行 CALL 指令的那一刻，调用者（caller）的栈指针 RSP 的值。

因为 call 指令会把返回地址压栈，所以：

  • **caller 的 RIP = Memory[CFA - 8]**（x86-64 上一个地址槽是 8 字节，返回地址正好在 CFA 下方 8 字节处）
  • caller 的 RSP = CFA

所以，只要在任意一条指令的位置都能算出 CFA，就能一层一层地往上还原出整个调用栈。

2.2 CFI 的「二维表格」模型

可以抽象地认为，CFI 为每一条汇编指令都隐式维护了一条这样的记录：

运行时指令地址 (RIP) CFA 的计算公式 返回地址 (RIP) 存放在哪 RBP 存放在哪 其他寄存器…
0x401100 (foo 入口) RSP + 8 cfa - 8 (栈上) 未改动 …
0x401101 (push rbp) RSP + 16 cfa - 8 (栈上) cfa - 16 …
0x401104 (mov rbp,rsp) RBP + 16 cfa - 8 (栈上) cfa - 16 …
… … … … …
0x401150 (pop rbp) RSP + 8 cfa - 8 (栈上) 未改动(已恢复) …

注意：这是一个「概念模型」。真实的 CFI 不会为每条指令存一整行，
而是存成一套「增量指令 + 位置偏移」的压缩字节码（见下节）。

3. CFI 的物理存储：.eh_frame

CFI 物理上存储在 **.eh_frame**（Exception Handler Frame）节中（调试用的还有 .debug_frame）。

由于上面那种「二维表格」极其庞大，存储时做了特殊优化，只保留两个条目：

  1. CIE（Common Information Entry，通用信息条目）
    包含同一个文件 / 同一函数族共享的全局配置，例如：

    • 架构的数据对齐因子（Data alignment factor）
    • 返回地址是哪个寄存器（Return address column）
    • 初始的 CFA 规则

  2. FDE（Frame Description Entry，帧描述条目）
    对应具体的 C/C++ 函数，包含：

    • 该函数的代码起止范围
    • 一串用于 DWARF 的字节码指令（DW_CFA_*），编码了 CFI 随 PC 位置动态变化的过程

.eh_frame 的来历

这个 section 最初是 GNU / GCC 在引入 C++ 异常处理机制（throw / catch）时设计的：

  • 当 C++ 代码抛出异常时，运行时库（如 libgcc_s 或 libc++abi）必须沿栈向上做 Stack Unwinding，
    一层层寻找匹配的 catch 块，并调用沿途局部对象的析构函数（RAII）。
  • 为了在没有 RBP（帧指针）、甚至开了 -O2 优化的代码里依然能精准回溯栈帧，
    GNU 把 DWARF 规范里的 CFI 标准搬了进来，专门放在 .eh_frame 里。
  • 虽然名字带 “Exception Handling”，但它不止用于 C++ 异常：现代 Linux 上的 gdb、backtrace()、dladdr、C++ 异常、
    以及许多 profiler，在 -fomit-frame-pointer 的情况下都依赖 .eh_frame 做准确的栈展开。

查看 .eh_frame 内容：readelf -wf <binary>。

4. DWARF Unwind 完整流程

  1. PMU 采样得到 RIP、RSP（性能分析场景）；或直接拿到当前 IP + 寄存器状态。
  2. DWARF Unwind 的入口是 IP + register state。
  3. 第一件事：根据 RIP 查 /proc/<pid>/maps，找到它所属的 module（哪个 .so / 可执行文件）。
  4. 在该 module 里找到 .eh_frame，再根据 RIP 定位到对应的 FDE
    （FDE 就是「描述某个特定 PC 地址范围的 unwind information」）。
  5. 开始解析 CFI（可用 readelf -wf 查看，里面的信息就是一套描述栈帧状态变化的指令）。
  6. 核心动作：读取 .eh_frame 中的 CFI 规则 → 根据当前 RIP 找到对应 FDE → 执行其中的 DW_CFA_* 指令 →
    得到当前 PC 对应的 CFI 状态 → 用该状态计算 CFA → 再按 Register Rule 恢复 caller 的 RIP、RSP、RBP 等寄存器。

对比两种方法，一眼看出差别：

  • FP unwind（上一篇）：约定俗成的固定公式
    • caller RBP = [RBP]
    • caller RIP = [RBP + 8]
  • DWARF unwind（本篇）：编译器提供的规则
    • caller RBP = 根据 CFI Rule
    • caller RIP = 根据 CFI Rule
    • caller RSP = 根据 CFI Rule
    • 不同函数通常有不同的 CFI Rule。

5.1 编译命令

好消息：GNU 帮我们封装好了 _Unwind_Backtrace 等函数，无需手写 CFI 解析器，直接调用即可完成栈回溯。

各 flag 的含义：

flag 作用
-g 生成 DWARF 调试信息（.debug_info 等，便于反汇编/阅读）
-O0 关闭优化，方便对照源码
-rdynamic 把本程序的函数符号导出到 .dynsym，dladdr 才能解析出名字

关键点：这里的 -fomit-frame-pointer 是故意加的——为了演示「即使没有 RBP，DWARF 也能回溯」。
反汇编会看到 baz/bar/foo/main 里根本没有 push rbp / mov rsp,rbp。

5.3 逐段讲解

  • **print_symbol(ip)**：用 dladdr 把一个地址符号化。若解析成功且有符号名，打印 名字+0x偏移；
    否则打印 ??。它复用了上一篇 FP unwind 里的符号化思路。
  • **unwind_callback(ctx, arg)**：_Unwind_Backtrace 每展开一帧就回调一次。
    每次从中取两个值：
    • _Unwind_GetIP(ctx)：当前这一帧的指令地址（RIP）。
    • _Unwind_GetCFA(ctx)：当前这一帧的 CFA。
      打印 深度 / IP / CFA / 符号，然后深度 +1。
    • 返回 _URC_NO_REASON 表示「继续往上展开」；ip == 0 时返回 _URC_END_OF_STACK 表示到达栈底。
  • **dwarf_unwind()**：入口函数，构造 depth=0 的上下文，调用 _Unwind_Backtrace(callback, &uc)。
  • **baz/bar/foo/main**：一条 4 层调用链，全部加 __attribute__((noinline)) 防止被内联掉。

关键：为什么用 -fomit-frame-pointer 也不怕？ 看看反汇编：

baz 全程没有碰 rbp，只通过 sub $0x8,%rsp 分配栈空间、add $0x8,%rsp 回收。
unwinder 之所以仍能正确回溯，靠的就是 .eh_frame 里记录的 DW_CFA_def_cfa_offset 等规则（见 5.5）。

5.4 运行结果解读

  • #0 ~ #4：本程序的 dwarf_unwind → baz → bar → foo → main，全部正确符号化（-rdynamic 的功劳）。
  • #0 的 IP 是 dwarf_unwind+0x37，正对应反汇编里 _Unwind_Backtrace 调用后的位置。
  • #5：是 libc 内部的一个函数，dladdr 拿不到符号名，显示 ??。
  • #6：__libc_start_main+0x80，#7：_start+0x25，这是 C 运行时（crt）的启动帧。
  • #8：IP = 0，即栈底（_start 之前没有 caller 了），回调返回 _URC_END_OF_STACK 结束。

CFA 的变化规律：从 #1 到 #5，每往上一层 CFA 增加 0x10（16 字节）——
正好是「sub $0x8,%rsp 的局部空间 8 字节 + call 压入的返回地址 8 字节」。
#0 → #1 增了 0x20，因为 dwarf_unwind 自己 sub $0x18,%rsp（24 字节）再加上返回地址 8 字节 = 32 字节。

5.5 用 readelf -wf 看真实的 CFI

readelf -wf dwarf_unwind 可以解开 .eh_frame，摘录关键部分：

逐条对照 baz 的反汇编：

  • CIE 里的 DW_CFA_def_cfa: r7 (rsp) ofs 8：默认 CFA = RSP + 8。
    因为 call 刚把返回地址压栈，此刻 RSP 指向返回地址，CFA（caller 的 rsp）正好是 RSP + 8。
  • CIE 里的 DW_CFA_offset: r16 (rip) at cfa-8：返回地址（寄存器 16 = RIP）保存在 CFA - 8。
  • FDE pc=13c9..13dc 覆盖 baz 整个函数。
  • DW_CFA_advance_loc: 8 to 13d1：位置推进 8 字节（endbr64(4) + sub $0x8,%rsp(4)），到达 call 之前。
  • DW_CFA_def_cfa_offset: 16：此后 CFA = RSP + 16（因为 rsp 被减了 8）。
  • DW_CFA_advance_loc: 10 to 13db：推进到 add $0x8,%rsp 之后、ret 之前。
  • DW_CFA_def_cfa_offset: 8：CFA = RSP + 8（rsp 恢复，准备 ret）。

这就是「没有帧指针也能展开」的真相：CFI 用 DW_CFA_def_cfa_offset 一路追踪 rsp 的变化，
unwinder 在任何 PC 位置都能算出 CFA，进而从 [CFA-8] 取出返回地址。

6. 关键点 & 易错点

  1. CFI 是编译器生成的「规则」，不是运行时算出来的；unwinder 只是照规则执行，不需要 RBP。
  2. CFA 是理解核心：它是 call 那一刻 caller 的 RSP；返回地址 = [CFA-8]（x86-64 的 8 字节槽），caller RSP = CFA。
  3. **.eh_frame vs .debug_frame**：运行时回溯用 .eh_frame（即便 strip 之后通常仍在）；
    .debug_frame 属于调试段，strip 后可能被移除。
  4. **符号化需要 -rdynamic**：否则本程序自己的 baz/bar/foo/main 不在 .dynsym 里，dladdr 解析不出来，只能显示 ??。
  5. CIE/FDE 是压缩字节码（DW_CFA_*），不是逐指令全量表格；用 readelf -wf 可以把它还原成人类可读的形式。
  6. -fomit-frame-pointer 下照样能回溯：因为 CFI 靠 DW_CFA_def_cfa_offset 追踪 rsp 变化，
    不依赖 push rbp / mov rsp,rbp 那套 FP 约定。
  7. 每帧的 CFA 递增规律：普通叶子帧（sub $0x8 + call）CFA 递增 16 字节；函数局部越大、增长越多。
  8. 跨 module 的帧：回溯从本程序的 main 自然走到 libc 的 __libc_start_main、_start，
    说明每个 module 各自维护自己的 .eh_frame，unwinder 按 IP 逐个 module 查找。
