编译与汇编

编译器的核心任务只有一个：把高级语言（C/C++ 纯文本）翻译成汇编语言（Assembly Code）。

在 GCC 中，这个过程可以通过 -S 选项来观察：

运行后，你会得到一个 main.s 文件，里面全是 mov, push, add 等低级汇编指令。

编译器在后台干的 5 件硬核事

在这个阶段，编译器（在 GCC 中其实是一个叫 cc1 或 cc1plus 的内部程序）会把你的代码送进一条精密的工业流水线：

1. 词法分析 (Lexical Analysis)

  • 做什么：把你的代码切碎。
  • 细节：它把一长串字符串切成一个个有意义的最小单元（Tokens）。比如 int A = 2; 会被切成：关键字(int)、标识符(A)、操作符(=)、常数(2)、分号(;)。

2. 语法分析 (Parsing)

  • 做什么：检查你有没有语法错误。
  • 细节：它把这些 Tokens 组合成一棵抽象语法树（AST, Abstract Syntax Tree）。如果你的括号没闭合，或者少写了分号，语法树就建不起来，编译器就会在这里当场报错（Syntax Error）。

3. 语义分析 (Semantic Analysis)

  • 做什么：检查代码在逻辑上是否说得通（类型检查、作用域检查）。

  • 细节：语法没问题，不代表逻辑没问题。例如：

    C++

4. 中间代码生成与优化 (IR & Optimization) 最核心的一步

  • 做什么：脱离具体的 CPU 架构，对代码逻辑进行疯狂优化。
  • 细节：编译器会把语法树转成一种“中间代码”（IR, Intermediate Representation）。在这个阶段，大名鼎鼎的编译优化（-O1, -O2, -O3）开始发威。
    • 常量折叠：你写 int x = 3 + 5;，优化器直接把它改成 int x = 8;。
    • 死代码消除：你写了 if(false) { ... }，优化器直接把里面的代码打包扔进垃圾桶。
    • 循环展开、内联函数：把函数调用直接拍平到调用处，减少压栈开销。

5. 目标代码生成 (Code Generation)

  • 做什么：根据你的目标硬件（x86-64, ARM, MIPS），翻译成对应的汇编代码。
  • 细节：将优化后的中间代码映射到具体的 CPU 寄存器上，生成最终的 .s 汇编文件。

编译阶段你必须认识的 GCC 核心参数

在实际工程（Makefile/CMake）中，我们通过以下参数来控制编译阶段：

参数 作用 工程实用场景
-S 只编译，不汇编 查看编译器到底把你的高级代码优化成了什么样。
-O0 / -O2 / -O3 优化等级 调试用 -O0（保留所有变量），发布用 -O2 或 -O3（性能最高）。
-Wall -Wextra 开启几乎所有警告 工程必带！ 让编译器化身严厉的导师，消灭潜伏的 Bug。
-std=c++17 指定语言标准 告诉编译器用哪一代的语法规则去解析 AST。

词法分析

什么是词法分析？

词法分析（Lexical Analysis）**是编译过程的**第一步**。它的任务是：把一长串连续的代码文本（字符串），切碎成一个个有独立语义的“最小单元”，并贴上标签。**

在编译原理中，这些切碎后的最小单元被称为 Token（词法记号）。负责干这个活的程序叫做词法分析器（Lexer 或 Scanner）。

你可以把它类比为英语翻译中的“断词”。比如有一串没有空格的英文字符 Ilovecomputer，词法分析器就会把它切分成 I (代词)、love (动词)、computer (名词)。

它的核心作用是什么？

为什么不直接拿字符串去生成汇编，非要多此一举切成 Token 呢？它在工程上有三个不可替代的作用：

1. 过滤噪声，减轻后续流水线的负担

代码里有大量的**空格、换行符、制表符（\t）**以及**注释**。这些东西是写给人类看的，CPU 根本不需要。

  • 词法分析器会在这个阶段把所有的注释和无用空格全部过滤掉。
  • 后面的“语法分析器”拿到的直接就是纯净的 Token 流，不需要再分心去处理“这里是不是有个注释”这种低级问题。

2. 初步分类，建立符号表雏形

当词法分析器遇到 A 时，它知道这是一个“标识符”（用户起的变量名或函数名）。它会把 A 收集起来，为后面语义分析要用的符号表（Symbol Table）打下基础。

3. 拦截最基础的“非法字符”错误

如果你的代码里不小心混入了极其离谱的字符（比如手抖打了个中文分号 ；，或者特殊符号 @），词法分析器在构建自动机时会失败，从而当场中断编译，抛出 “Lexical Error”（词法错误：未知字符）。

词法分析的眼光非常局限，它只认单词，不看句子。

比如你写了这样一行毁灭性的代码：

  • 词法分析器： “没问题！int 是关键字，= 是操作符，2 是数字… 每一个词我都认识，词法通过！”
  • 结果： 这一行代码会顺利通过词法分析。直到进入下一步语法分析时，编译器才会发现“这些词组合在一起根本不符合 C++ 语法规则”，然后报错。

简单来说，词法分析只负责检查“有没有错别字”，至于“句式对不对”，那是下一步语法分析（Parsing）的职责了。

语法分析

如果说词法分析是把一堆字母拼成“单词”，那么**语法分析（Syntax Analysis / Parsing）**就是把这些单词组合成“句子”，并检查这个句子是否符合 C++ 语言的**“语法结构规则”**。

干这个活的程序叫做语法分析器（Parser）。它接收上一步切好的 Token 流，然后像我们小时候分析英语句式（主谓宾）一样，把Token流组装成一棵结构化的树——抽象语法树（AST, Abstract Syntax Tree）。

语法分析的核心作用

1. 拦截“句式结构错误” (Syntax Error)

这是我们平时写代码最常遇到的报错阶段。如果你的代码不符合句法规则，比如：

  • int A = ; （赋值号后面没有表达式）
  • if (A == 2 （括号没有闭合）

当语法分析器尝试把这些 Token 塞进对应的语法树模型时，发现“缺胳膊少腿”，就会立刻中断编译，抛出经典的 syntax error（语法错误），并精准指出在哪一行哪一列。

2. 生成抽象语法树 (AST， Abstract Syntax Tree)

AST 是编译器后台最重要的数据结构。一旦这棵树建立成功，后续的“语义分析（检查类型）”、“中间代码生成”以及“代码优化”，全部都是基于对这棵 AST 进行遍历和修改来完成的。

AST 是 Abstract Syntax Tree（抽象语法树） 的缩写。

它是源代码在编译器内存中的树状几何表达。

  • “树”：因为代码具有层级和嵌套关系（比如函数包含循环，循环包含判断），用树状的分支结构表达最天然。

  • “抽象”：因为它无视了代码中不重要的细节。比如代码里的空格、换行、甚至是用来强制优先级的**括号 ()**，在变成 AST 时都会被丢弃。AST 只保留核心的语法骨架。

  • 一句话解释：因为在树状结构中，越位于“底层（子节点）”的代码，越会被先计算；越位于“顶层（根节点）”的代码，越后计算。

  • 语法分析器在建树的时候，就已经把数学结合律、操作符优先级、括号等规则，固化成了树的深度层级。

语义分析

如果说词法分析是看“有没有错别词”，语法分析是看“句子结构合不合语法”，那么**语义分析（Semantic Analysis）**就是看**“这个句子逻辑上到底说不说得通”**。

干这个活的程序叫语义分析器（Semantic Analyzer）。它会结合上下文、变量类型、作用域等规则，对上一步生成的 AST（抽象语法树）进行全方位的“逻辑大体检”。

在 C++ 中，**静态类型检查（Static Type Checking）**和**符号表（Symbol Table）管理**是语义分析绝对的核心。

语义分析主要抓哪些“现行犯”？

中间代码生成与优化

到了这一步，代码已经顺利通过了词法、语法和语义的“三重大体检”，被证实是一段完全合法、没有逻辑漏洞的代码。

接下来的阶段，编译器要干两件非常硬核的事：中间代码生成（IR Generation） 与 代码优化（Optimization）。

一、 中间代码生成 (IR Generation)

什么是 IR？

IR 是 Intermediate Representation（中间表达/中间代码） 的缩写。

编译器不会直接把带有高层逻辑的 Annotated AST 瞬间翻译成底层的汇编代码（比如 x86 或 ARM 汇编），因为那样太粗暴、太难写了。相反，它会把 AST “拍平”，生成一种独立于具体 CPU 架构的、类似于汇编语言的虚拟代码。最著名的 IR 例子就是 LLVM IR。

为什么要多此一举生成中间代码？（工程艺术）

假设市面上有 4 种高级语言（C++, Rust, Swift, Go），同时有 4 种 CPU 架构（x86, ARM, RISC-V, MIPS）。

  • 没有 IR 的世界： 你需要为每种语言针对每种硬件写一个编译器，总共需要写 $4 \times 4 = 16$ 个编译器。
  • 有 IR 的世界：
    • 前端（Frontend）： 负责把 C++/Rust/Swift 翻译成统一的 IR。
    • 后端（Backend）： 负责把这套统一的 IR 翻译成对应的 x86/ARM 汇编。
    • 这样只需要写 $4 + 4 = 8$ 个模块！而且最强大的优化算法只需要针对 IR 写一套，所有语言、所有硬件都能同时享受！

典型的 IR 长什么样？（三地址码 Three-Address Code）

IR 通常采用“三地址码”的形式，即每一行指令最多只能有两个操作数和一个结果。

一个让你感到后怕的“工程陷阱”：未定义行为 (Undefined Behavior)

优化器是完全基于“数学逻辑和语言标准”来运行的。它在优化时有一个至高无上的前提：假设程序员写出来的代码完全符合 C++ 标准，绝对没有违反规则。

如果你写了未定义行为（UB）的代码，优化器就会产生极其诡异的优化，导致完全偏离你的预期。比如：

  • 人类的直觉： “虽然顺序写反了，但好歹有个 if 检查，应该能防住空指针吧？”
  • 优化器的神逻辑：
    1. 看到第一行 int value = *ptr;，优化器想：“既然程序员敢解引用 ptr，根据 C++ 标准，ptr 在这里绝对不可能是 nullptr（否则就是非法崩溃）。”
    2. 看到第二行 if (ptr == nullptr)，优化器乐了：“根据我刚才的推导，ptr 必定不为空，所以这个 if 条件永远为 false！”
    3. 触发 死代码消除！直接把整个 if 语句全部删掉。
  • 最终结果： 这个防空指针的 if 块在最终的程序里根本不存在。

总结

  • 中间代码生成： 是把树状的高级语言，降维成一维的、架构无关的虚拟三地址码（IR），实现了前后端分离。
  • 代码优化： 是拿着这套 IR，进行逻辑上的数学去重、剪枝、合并，用极高的编译期计算，换取运行期极限的执行速度。

通过了优化的 IR，终于可以精疲力尽地进入最后一步——目标代码生成（Code Generation），让后端根据具体的 CPU，吐出真正的汇编和机器码了。

生成目标代码

1. 寄存器分配 (Register Allocation) —— 压榨 CPU 核心

这是后端最难、也是最核心的任务。

  • 面临的矛盾： 之前生成的中间代码（IR）可以使用无限多个虚拟寄存器（比如 %t1, %t2, %t100...）。但现实是残酷的，物理 CPU 上的通用寄存器数量少得可怜（比如 Intel x86-64 只有 16 个，ARM64 只有 31 个）。
  • 编译器的做法： 后端会使用图着色算法（Graph Coloring），极其聪明地计算出哪些变量最常用、最倒霉。把高频使用的变量分配到珍贵的 CPU 寄存器里，把低频的变量踢到慢得多的 内存（栈空间） 内存中。

2. 指令选择 (Instruction Selection) —— 熟知硬件绝活

不同的 CPU 指令集，长处完全不同。后端必须是一个“硬件百事通”，用最优的物理指令去实现 IR 的逻辑。

  • 例如，IR 里有一行代码是把一个整数乘以 4（x = y * 4）。
  • 平庸的后端： 翻译成乘法指令 imul。
  • 聪明的后端： 熟知 CPU 的位移操作比乘法快得多，直接翻译成左移两位指令 shl。
  • 如果开启了高级指令集（如 -mavx2），后端还会选择用 SIMD（单指令多数据） 向量指令，让 CPU 一个指令同时算 8 个浮点数。

3. 指令调度 (Instruction Scheduling) —— 流水线防堵车

现代 CPU 内部是有指令流水线（Pipeline）的，如果前后两行指令有强烈的依赖关系（比如第二行必须等第一行从内存读完数据才能算），CPU 就会陷入停顿（Stall）摸鱼。

  • 后端会重新排列汇编指令的顺序，在两行有依赖的指令中间，穿插一些无关的独立指令，把 CPU 流水线塞满，防止硬件发生“气泡（Bubble）”。

编译阶段的终点：生成 .o 目标文件

当后端把寄存器分好、指令调好后，它会吐出 .s 汇编。

汇编

1. 编译阶段（Compilation）

  • 执行者： cc1plus（GCC 的 C++ 编译器前端+优化器+后端）。
  • 输入： 预处理后的纯文本（.i）。
  • 输出： 汇编语言文本（.s）。
  • 本质： 复杂的“逻辑语法翻译”，此时依然是人类可读的文字（如 mov eax, 1）。

2. 汇编阶段（Assembling）

  • 执行者： as（GNU 汇编器，Assembler）。
  • 输入： 汇编语言文本（.s）。
  • 输出： 二进制机器码目标文件（.o 或 .obj）。
  • 本质： 极其机械的“查表翻译”。汇编器里有一张对照表，看到 mov 就换成对应的二进制硬编码（如 0x89），不需要任何复杂的语法分析或性能优化。

汇编（Assembling） 的过程，用一句话概括就是：“查表翻译”。

在物理层面上，它由一个独立的工具（在 Linux 上叫 as，即 GNU Assembler）执行。它接收上一步编译出来的 汇编文本文件（.s），将其翻译成 CPU 能够直接执行的 二进制机器码，并打包成 目标对象文件（.o 或 .obj）。

与前面充满“高深数学和激进优化”的编译阶段不同，汇编阶段非常机械纯粹——它没有复杂的语法树，也不做性能优化，纯粹是“按部就班地把文字换成数字”。

1. 汇编器在后台具体干了什么？

汇编器从上到下逐行扫描 .s 文件，主要执行以下三个核心动作：

A. 助记符转机器码（Opcode Mapping）

CPU 根本看不懂 mov、add、push 这样的英文单词（这些叫助记符）。CPU 只认特定的二进制硬编码（操作码，Opcode）。

  • 汇编器内部自带一张针对特定 CPU 架构的硬编码对照表。
  • 扫描到 mov eax, 1 ➔ 查表 ➔ 替换成十六进制数据（例如 B8 01 00 00 00）。

B. 符号收集与地址计算

你在写汇编时，会看到很多“标签（Labels）”，比如循环的跳转点或函数入口：

代码段

CPU 同样不懂什么是 .L2。汇编器在扫描时，会计算出 .L2 这一行指令在当前代码段中的相对字节偏移量。

  • 如果计算出 .L2 距离当前跳转指令是往回数 12 个字节，汇编器就会把 jl .L2 翻译成类似 EB F4（F4 是 -12 的补码）的机器码。
  • 这就把人类可读的“名字标签”变成了机器可读的“相对物理距离”。

C. 数据与指令分流（划分 Section）

汇编器会根据汇编代码中的指示（如 .text、.data），把机器指令和全局变量分别归类，整齐地塞进最终 .o 文件的不同格子（段/Section）里。

2. 汇编产物 .o 文件大拆解

汇编结束后的产物是 目标文件（Object File）。它是一个已经符合操作系统二进制规范（Linux 的 ELF，Mac 的 Mach-O，Windows 的 PE）的“毛坯房”。

3. 汇编阶段留下的工程“扣子”：重定位表

汇编器是极其“短视”的，它一次只处理一个文件。

假设你的 main.cpp 调用了 B.h 里的一个函数 void func_in_B()：

  1. 汇编器在处理 main.s 时，扫描到了 call func_in_B 这条指令。

  2. 汇编器去自己的文件里翻了个遍，破口大骂：“我这个文件里根本没有 func_in_B 的定义，我上哪知道它的物理内存地址去？！”

  3. 汇编器的妥协做法： 它在机器码里留下 4 个字节的空白（全填 00 00 00 00），然后在 重定位表（Relocation Table） 里狠狠记上一笔：

    “在 .text 段的第 0x24 字节处，有一个叫 func_in_B 的函数调用。我现在填的是假地址 0。未来的链接器（Linker）老哥，你把各个 .o 文件拼起来的时候，记得把这里改成真正的地址！”

汇编器做的工作不多，所以一下就讲完了。
