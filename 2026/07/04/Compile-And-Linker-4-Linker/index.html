-V --version-info 查看版本符号信息 打印 .gnu.version、.gnu.version_d 和 .gnu.version_r 段，展示动态链接库的符号版本控制（如 GLIBC_2.2.5）。
-n --notes 查看核心注释段（Note） 打印 .note.ABI-tag 或 .note.gnu.build-id。通常包含编译器的 ABI 版本要求或唯一的构建 ID（Build ID）。

ELF 文件布局

文件头：readelf -h main

以下跳过一些不重要的字段，重点分析关键信息。

前 4 个字节已经可以标识 ELF 文件。各字段含义如下：

  • byte 5：架构位数（32/64 bit）
  • byte 6：大小端
  • byte 7：ELF 版本号
  • byte 8：目标系统的 OS ABI
  • byte 9~16：zero padding

该字段对应 byte 5。可选值：ELF32、ELF64。

该字段对应 byte 6。可选值：2's complement, little endian、2's complement, big endian。

该字段对应 byte 8。常见值包括：HP-UX、NetBSD、Linux、SUN Solaris、FreeBSD、ARM architecture（ARM 裸机）、OpenBSD。

几乎没有变过，Linux 的 ABI 异常的稳定。实际上 ABI 兼容的处理大多都是用 SONAME 做平替了。

此字段标识 ELF 文件的类型，几种核心类型如下：

  • REL（Relocatable）：虚拟地址未分配（全是 0），内部充满地址”欠条”。==操作系统内核（kernel）绝对无法直接加载运行它。==
  • EXEC（Executable）：拥有绝对固定的内存加载地址（入口地址）。过去老版本的 Linux 可执行文件全是这个类型。现在如果编译时强行加 -no-pie 参数，产出的程序也会是这个类型，其实就是 -NO-PIE 文件。
  • DYN（Shared Object / PIE）：==其实就是 PIE 文件（Position-Independent Executable），也是现代 Linux 发行版的默认输出类型。==
  • CORE（Core Dump）：核心转储文件（即 core dump 崩溃快照）。当 C++ 程序发生段错误（Segmentation fault）崩溃时，内核如果开启了限制，就会把当前程序在内存里的所有状态（堆栈、寄存器状态）直接 dump 成一个 CORE 文件，供 gdb 进行死因解剖。

常见架构标识：

Machine 值 对应架构 说明
Intel 80386 32 位 x86 架构（i386/x86） 经典的 32 位 x86
ARM 32 位 ARM 架构 移动端与嵌入式广泛使用
Advanced Micro Devices X86-64 64 位 x86 架构（x86-64 / AMD64） 当前主流桌面与服务器架构
AArch64 64 位 ARM 架构 现代 ARM 服务器与手机架构
RISC-V 开源 RISC-V 架构 RV32、RV64、RV128 统一标记，核心指令集编码完全一样，区别仅为寄存器位宽（XLEN）

当你在终端输入 ./main 时，Linux 内核的 binfmt_elf.c 模块会瞬间读取这个字段，并和当前 CPU 的物理架构进行比对：

  • 硬件不匹配（直接拒绝）：如果你把这个 X86-64 的 main 文件拷贝到一部 ARM64 架构的设备里运行，内核一读 Machine 字段发现是 62（x86-64），而当前 CPU 汇报的硬件环境是 183（AArch64），内核会立刻返回 ENOEXEC 错误，==根本不会把这些读不懂的异构机器码塞进内存。==
  • 兼容模式（向下兼容）：如果你在 64 位 x86 系统上运行一个老旧的 32 位 i386 程序，内核读到 Machine: 3，会判断当前 CPU 具备 32 位兼容硬件电路，于是为这个进程初始化一套 32 位的虚拟内存环境，让老代码安全运行。

在终端敲下 ./main 并按下回车后，操作系统内核把这个文件加载到内存里，CPU 执行的第一条机器指令就在这个地址上。这个 0x10e0 指向的是 C 语言运行时库（CRT）注入的 _start 函数。

执行流程：

内核加载器 → 0x10e0（_start） → __libc_start_main → 构造函数 → int main() → 析构函数 → exit

那么怎么和 PIE 对应呢？

  1. 内核拉起进程，随机产生一个基地址（Base Address），比如：0x555555554000
  2. 内核读取 ELF 头，发现 Entry point 是 0x10e0
  3. 内核将两者相加：$0x555555554000 + 0x10e0 = 0x5555555550e0$
  4. 内核正式把 CPU 的 RIP 寄存器（指令指针）指向 0x5555555550e0，程序开始运转

注意：REL 文件的 entry point 为 0；.so 文件的入口地址一般会指向内部的一个 _init 函数，用来做加载时的自检。

这是一个极其关键的文件内部物理定位指针。从文件第 64 字节开始的地方，就是真正指导如何把这个文件加载进物理内存的程序头表。64 字节这个数字并不巧——因为它刚好是 ELF_Header 结构体的大小。

在文件的物理排列上，它们是严丝合缝、一字节不差地紧挨着的：

  • 0 ~ 63 字节：存放的是 ELF Header 自身（魔数、架构、版本等）
  • 第 64 字节：ELF Header 结束，程序头表（Program Headers）无缝接棒，正式开始

那么，什么是程序头表呢？

==操作系统内核在通过 execve 准备运行你的 main 程序时，其实是非常”功利”的。内核根本不关心你代码里细分的 .text（代码段）、.rodata（只读数据段）或者 .data（读写数据段）。内核只看程序头表。==

程序头表由若干个大小固定的表项（在 64 位系统下每项 56 字节）组成。每一行都像一条指令，指挥内核在内存中圈地。例如：

  • 指令 1（LOAD 段）：”把文件从偏移量 0x0 开始、大小为 0x2000 字节的内容，加载到虚拟内存的某个随机基地址去，权限给可读、可执行（R E）。”——这里面其实就打包了你的所有代码和只读常量。
  • 指令 2（LOAD 段）：”把文件后面偏移 0x2000 开始、大小为 0x500 字节的内容，加载到内存中紧随其后的位置，权限给可读、可写（RW）。”——这里面打包了你的全局变量、静态变量。

注意：REL 文件也没有程序头表，因为它还没有链接，没办法真正独立运行。

Start of section headers: 14656 (bytes into file) 是 ELF 蓝图里另外一张极其庞大的施工图指针。

如果说前一个 Start of program headers: 64 是给操作系统内核看的”粗放型”内存映射表，那么这里的 Start of section headers: 14656 就是专门给编译器、链接器和调试器（如 g++、ld、gdb）看的”精细化”分工表。

这个字段的意思是：

“从文件第 14656 字节（已经到了文件的尾部区域）开始的地方，存放着整个 ELF 文件的 Section Headers（节头表）。”

Section Headers（节头表），就是一目了然的目录，记录了每一个节的名字是什么、在文件的什么偏移位置、占多少字节。

为什么它的位置这么靠后？（14656 字节）

你会发现，Program Headers 在第 64 字节就开始了，为什么 Section Headers 要被发配到第 14656 字节这么靠后的地方？

==这是因为在 ELF 文件的物理排布中，节头表默认是”垫底”的。==

一个经典的成品 ELF 文件，其物理结构就像一个汉堡包：

  1. 最上层（面饼）：ELF Header（0 ~ 63 字节）
  2. 上层夹心（酱料）：Program Headers（64 字节开始，紧跟其后）
  3. 核心实体（牛肉）：真正长长的数据肉块（.text、.rodata 等机器码和数据）
  4. 最底层（面饼底）：Section Headers（节头表），它被安放在文件的最后。链接器把所有的数据（14000 多字节）全部写完之后，才在文件的末尾贴上这张最终的目录索引。

内核加载 vs 链接调试：两张表的终极分工

这就引出了 ELF 架构设计中最为核心的”双重视图（Dual View）”哲学：

  • 运行程序时（内核视角）：内核通过 execve 启动 ./main 时，==完全不需要看节头表（Section Headers）。==内核只读 Program Headers 知道怎么分配内存就行了。这也是为什么很多在线上部署的生产环境中，大家会用 strip main 命令直接把文件的节头表强行删掉来缩减文件体积（比如从 14KB 缩减到 6KB）。即使删除了第 14656 字节后面的所有内容，程序依然能完美独立运行。
  • 开发调试时（链接、调试器视角）：当你在用 g++ 链接多个 .o，或者用 gdb 打断点、看符号变量，或者用 objdump 分析时，这些工具必须依赖第 14656 字节的 Section Headers。没有它，gdb 面对一坨裸机器码，根本认不出哪里是 .text，哪里是你的函数。

ELF Header 自身的大小，64 字节。

56 字节：是程序头表里一个表项（Program Header Entry）的大小。程序头表可能包含多个这样的表项。

总共有 13 个 program headers。

每个 section header 有 64 字节大小。

总共有 31 个 section headers。

“整个文件里所有 Section（节）的名字（比如 .text、.data、.rodata 这一串字符串），全部打包藏在第 30 个 Section 盒子里！”这个存放全文件所有节名字的特殊盒子，就叫 .shstrtab（Section Header String Table，节头字符串表）。这是因为字符串一般是不定长的，所以用了单独一个 section 来记录。

字符串使用过程大概是这样的：

当你在终端敲下 readelf -S main（查看所有节的详情）时，readelf 工具在底层执行了一个完美的”按图索骥”流程：

  1. readelf 先读 ELF Header，看到 Section header string table index: 30
  2. 它立刻跳到第 30 个 Section Header 结构体，读出这个特殊盒子在文件中的物理起点（Offset）
  3. 接下来，当它去解析第 1 个盒子（比如 .text 段）时，.text 的结构体里写着：sh_name = 23
  4. readelf 就跑到第 30 个盒子的起点，往后挪 23 个字节，探头一读，刚好读到了 . t e x t \0 这几个字符

程序头表详解：readelf -l main

==内核加载器不认识 31 个 section，只认识这 13 个大 segment。==内核会把多个功能类似的 Section 打包揉碎，塞进同一个 Segment 里一股脑搬进内存。

Type：段类型

Segment 本身在硬盘上确实没有独立的数据实体，它只是一个”空壳”和”剧本”；真正的”肉块”全都整整齐齐地码在 Section（节）里面。所以，在进行静态分析、查看代码或常量时，你完全只需要去读取 Section 就可以了。

PHDR（Program Header Table）

这个段告诉内核：”我自己这 13 个 Program Header 被加载到虚拟内存的什么地方了。” 主要是为了让动态链接器（ld.so）在后续运行时，能够找到这个账本，从而知道当前进程有哪些动态加载的内存块。

LOAD（Load Segment）

==这是唯一负责把硬盘上的机器码、常量、全局变量搬进内存的段。==你在前面看到的 4 个 LOAD 段，就是通过内核进行页映射（mmap），把文件数据变成 CPU 可以直接执行的虚拟内存地址。

INTERP（Interpreter）

它里面只存了一个硬编码的字符串：[Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]。内核一旦看到这个 Type，就会在把你的程序拉进内存后，立刻把 CPU 的控制权移交给这个 ld-linux 解释器，让它先去帮你的程序把依赖的 .so 库全部找到、加载并绑定好符号，然后才真正跳到你的 main 函数去执行。

DYNAMIC（Dynamic Linking Information）

这个段对应了底部的 .dynamic 节。里面是一组组 Tag-Value 的键值对，详细记录了：这个程序依赖哪些库、动态符号表在哪里、重定位表在哪里。动态链接器就是靠读这个段的内容来帮你”接线”的。

NOTE（Note Section）

通常存放厂商或编译器注入的辅助信息。比如你的 08 号段 .note.ABI-tag，里面记录了当前二进制文件要求 Linux 内核的最低版本是多少。

GNU_PROPERTY（GNU Property Note）

现代 CPU 提供了很多硬件级安全特性（比如 Intel 的 IBT、CET 间接分支跟踪技术，防 ROP 攻击）。这个段告诉内核：本程序在编译时已经做好了适配，可以安全地开启这些最新的硬件级 CPU 防御。

GNU_EH_FRAME

它指向 .eh_frame_hdr。当你在 C++ 里写了 throw 抛出异常，或者程序崩溃需要打印堆栈（Stack Trace）时，系统需要知道怎么一层层往回剥离函数调用栈（Stack Unwinding）。这个段里存的正是指导系统如何安全回溯堆栈的精密表格。

GNU_STACK（Stack Execution Flag）

看你输出里的权限：Flags: RW。==这里面最硬核的是，它没有 E（可执行）权限！== 早期黑客最喜欢的攻击手段是往局部变量（栈）里灌入一段恶意机器码，然后修改返回地址让 CPU 去栈里执行。编译器吐出这个 Type 就是在命令内核：”把这个进程的栈内存设置为不可执行（NX/DEP 技术）”，直接从底层废了栈溢出攻击的可行性。

GNU_RELRO（Read-Only After Relocation）

这是一种极其重要的安全加固技术。像动态链接的 GOT（全局偏移表），在程序刚启动时，动态链接器必须对它进行写入（把外部函数的真实地址填进去）。可一旦填完，这个表如果不加保护，运行时就可能被黑客通过内存漏洞篡改。内核看到 GNU_RELRO 这个 Type，就会在动态链接器把活干完的刹那间，强行把这片内存的权限从 RW 降级改为 R（只读）。

Offset

当前 Segment 相对于文件开始的偏移。

VirtAddr 和 PhysAddr

  • VirtAddr：某个段被加载到的虚拟地址，虽然有 ASLR 使其加上某个随机偏移（Random Offset），但相对偏移关系保持不变。
  • PhysAddr：在有 MMU 的系统上基本没有参考意义，因为反正也不会按照这个来。==只有没有 MMU 的 CPU 上，这个字段才有实际意义。==

FileSiz 和 MemSiz

  • FileSiz（文件大小）：这一段在硬盘文件里，实打实占据了多少个字节。
  • MemSiz（内存大小）：这一段被内核搬到虚拟内存后，总共要吃掉多少个字节的内存空间。

在绝大多数情况下，这两个值完全相等（比如输出里的 02 号、03 号、04 号 LOAD 段，甚至 PHDR、INTERP 段，数据全都一模一样）。

但是第 5 个段凭空多出来了 328 个字节，这是因为第 5 个 segment 包含了 .bss 段。==.bss 段在文件中不占空间（全部是 0），但在内存中必须分配并清零，所以 MemSiz > FileSiz。==

Align：对齐

凡是 Type 为 LOAD 的段，Align 都是 0x1000（4096），刚好是一个 page size。

硬件限制：CPU 没办法对 200 字节设置”可读可执行”，对紧挨着的下 200 字节设置”纯只读”。要设置权限，必须一整页（4KB）一整页地发通行证。

链接器的配合：链接器必须保证，每一个 LOAD 段在虚拟内存里的起始地址（VirtAddr），都必须是 4096 的整数倍（比如你的 0x0000、0x1000、0x2000，它们低 12 位全是 0，全部完美对齐 4KB 边界）。

既然 LOAD 段为了迎合 CPU 硬件强行对齐了 4KB，为什么夹在里面的 PHDR、DYNAMIC、NOTE 却只要 0x8 或 0x4 呢？

==因为这些段不需要操作系统为其独立开辟、映射新的内存页。它们本身就是借宿在某个 LOAD 段内部的”二房东”！==

比如看底部的映射表，DYNAMIC 段（编号 06）在物理上其实是包含在 05 号 LOAD 段里面的。既然 LOAD 段已经帮它把 4KB 的大框架对齐好了，那 DYNAMIC 只需要考虑自己在内部的结构体对齐就行了。

在 64 位（x86_64）CPU 中，数据总线一次性最喜欢吞吐 8 个字节（64 位） 的数据。

  • DYNAMIC 段里面全是一个个由”8 字节 Tag + 8 字节 Value”组成的 16 字节固定结构体
  • 如果这个段的起始地址对齐到 0x8（8 的倍数），CPU 读里面每一个成员时，都能在一个内存周期内一步到位
  • 如果不对齐 8 字节（比如从奇数地址开始），CPU 想要读一个 8 字节的指针，就必须捏着鼻子读两次内存，再把高低字节拼接起来，运行效率会瞬间暴跌

只有 INTERP 段的 Align 是 0x1。0x1 意味着”不需要任何对齐，随缘摆放”。

为什么它这么任性？因为 INTERP 段里面存的不是结构体，不是数字，也不是机器码，而是一串纯文本字符串："/lib64/ld-linux-x86-64.so.2\0"。

CPU 或者是内核读取它的时候，本来就是按照 char 字符一个字节一个字节往后挪着读的（sizeof(char) == 1）。既然怎么读都是单字节吞吐，链接器也就没必要为了它在后面填充一堆无用的 0x00 去强行对齐了。能省一个字节是一个字节。

仔细看，你可能会发现有些 Section “脚踩两只船”，比如：

  • .dynamic 同时出现在了 05 号、06 号和 12 号 Segment 里

一句话总结

==Section 没有被大卸八块，它只是被多次”标记”了。==

这群 Segment 就像是不同的部门经理，各怀鬼胎地看着同一批 Section 零件：

  • 搬运经理（LOAD）说：”这堆零件我得搬到内存里去。”
  • 安全经理（RELRO）说：”这堆零件等会儿干完活得加锁，不准别人改。”
  • 链接经理（DYNAMIC）说：”这堆零件里面写着我要找的动态库账本。”

Section 详解

readelf -S 输出详解

Type 字段

PROGBITS（Program Bits，程序数据）：这是 ELF 文件中最常见的 Type。它告诉系统：这个节里的内容是编译器生成的有效信息，不管是机器指令、还是各种硬编码的数据，在硬盘上必须占用实际空间。

NOBITS（No Bits，空头支票）：这个 Type 极其特殊。它专门给未初始化的全局变量（.bss）使用。它告诉链接器：==这个节在硬盘文件里不需要分配任何字节去存一堆 0（省硬盘空间），但当程序加载到内存时，必须按照 Size 划拨对应大小的虚拟内存，并强制全部清零（零页映射）。==

DYNSYM（Dynamic Symbol Table，动态符号表）：记录了程序跑起来后，必须暴露给动态链接器或者向外部引用的符号（比如 std::cout、main 函数）。每个符号占用固定大小的结构体（64 位下为 24 字节）。

STRTAB（String Table，字符串表）：专门用来存放密密麻麻的纯文本字符串（以 \0 结尾）。因为符号表（DYNSYM/SYMTAB）里的结构体很死板，放不下长短不一的函数名字符串（如 _ZSt4cout），所以符号表里只存一个数字指针（偏移量），真正的名字字符串全部集中塞在 STRTAB 类型的节里。

RELA（Relocation with Addend，带加数的重定位表）：由于 ASLR 导致内存地址每次启动都变化，程序在编译时根本不知道 std::cout 在内存的什么地方。RELA 类型的节里记录了一张张修正清单，动态链接器在启动程序时，会挨个读取 RELA 里的条目，把外部库函数的真正运行时地址填入 GOT 表。

**NOTE**：存放编译器或操作系统内核用来对齐物理特性、检测二进制合规性的特殊元数据（如编译特性的支持情况、最低内核版本限制）。

**INIT_ARRAY 和 FINI_ARRAY**：存放构造函数和析构函数的函数指针数组。

GNU_HASH（GNU Hash Table，哈希加速表）：动态链接器在外部库里找 std::cout 字符串时，如果挨个去遍历几万个函数名会极其缓慢。GNU_HASH 用哈希算法对所有动态符号建立了索引结构，让动态链接器可以在 $\mathcal{O}(1)$ 的时间复杂度内瞬间定位到函数地址。

EntSize（Entry Size）

如果这个 Section 盒子里装的是一个固定大小的结构体数组，那么 EntSize 就是每一个结构体成员占用的字节数。如果里面装的是长短不一的数据（比如 C++ 机器码、或者一串文本），由于无法切片，EntSize 就直接写 **0**。

比如 [6] .dynsym（动态符号表）：它的 Size 是 0x150（336 字节），而它的 EntSize 是 0x18（十进制 24 字节）。那么 $336 \div 24 = 14$，总共有 14 个动态符号表条目。

如果是 .text，它的 EntSize 就是 0，这是因为 C++ 函数指令长短不一，没有固定大小，所以只能是 0。

Link：指定它的”名字字典”是谁

符号表里的结构体都是死板的固定长度，根本塞不下类似 _ZSt4cout 这样长短不一的字符串。它里面只有一个叫 st_name 的数字偏移。Link = 7 就是在告诉工具：”别在这瞎找名字了，拿着我给你的数字，去 [7] 号 Section（也就是 .dynstr 动态字符串表） 里顺藤摸瓜，就能把真正的名字字符串抠出来。”

Info

Info 装的不是节编号，而是一个纯数字计数器。在符号表里，所有的局部符号（Local）必须排在前面，全局符号（Global）排在后面。Info = 1 意味着：”前 1 个条目（即索引 0）是本地占位符，从 第 1 个条目开始，后面全是大名鼎鼎的全局跨库符号。” 这样动态链接器一上来就能跳过本地符号，极大地提高了查找效率。

Link 的角色高度统一，基本都是扮演”只读数据源/字典”的引路人（通常是符号表或字符串表）；而 Info 的角色则是编译器架构师的”万能口袋”，在不同的 Section 类别下，其功能完全因地制宜。

Key To Flags

A（Alloc）：必须要分配内存。

X（Execute）：可执行。

W（Write）：可写。

M（Merge）：可合并。

S（Strings）：字符串。通常两个标志会一起出现（MS），比如 [27] .comment 节。它告诉链接器：这里面装的全部是只读的、以 \0 结尾的纯文本字符串。如果不同的 .o 文件里都包含了相同的字符串（比如都有一句 "GCC: (Ubuntu 11.4.0)"），链接器在最终打包时，只保留一份，剩下的全部剔除，以此极致压榨文件体积。

I（Info / 包含信息）：I 标志不是”内含信息”，它是编译器打的一个补丁标签，意思是：”请注意，我这节的 Info 字段里装的是另一个 Section 的编号，允许工具顺着它去跨节联动。”如果没有 I 标志的话，那么 Info 字段可能就是别的功能。

L（Link Order）：告诉链接器，在最终拼装二进制文件时，这个节必须严格按照某种特定的顺序排列，不能乱序。官方规范叫它 Link Order，用大白话翻译就是：**”空间对齐，按序排队”**。它规定了在最终打包二进制文件时，打上了 L 标志的多个 Section，必须严格按照它们所依赖的另一个符号表的顺序，在内存里整整齐齐地排列，绝对不准插队或乱序。

这个标志在日常的 C 语言开发中极少露面，但在现代 C++ 的异常处理（Exception Handling）和调试信息（Debugging）里，它扮演着至关重要的幕后角色：按需排列便于查找，CPU 和 GDB 的效率都会大幅提高。

G（Group / 组）：C++ 模板类、内联函数（Inline）专属。C++ 编译时，由于多个 .cpp 可能会重复展开同一个模板，编译器会把它们打包成一个 Group 并盖上 G 戳。链接器看到后，会自动把重复的组安全地删掉只剩一个，防止报”符号重定义”错误。

T（TLS / 线程局部存储）：如果你在 C++ 里写了 thread_local int static_val;，这个变量就会被打了 T 标志。它意味着每个线程启动时，都会单独复制一份该变量的独立副本，线程之间互不干扰。

C（Compressed / 压缩）：代表这个 Section 在硬盘上是被 zlib 等算法压缩过的，通常用于庞大的调试信息节（.debug_info），读取时需要解压。

E（Exclude / 排除）：告诉链接器，在最终生成动态库或可执行文件时，把这个节彻底抛弃，不要打包进去。

l（Large / 大数据）：x86_64 架构特殊优化。告诉编译器这个节包含超大对象（比如几个 GB 的静态数组），在寻址时需要使用特殊的巨型指针指令。

[5] .dynstr：动态字符串表

==.dynstr 的 Flags 必须带有 A (Alloc)。== 这意味着，当操作系统内核（Kernel）执行 execve 启动你的程序时，.dynstr 里的每一个字符串都会被原封不动地搬进进程的虚拟内存空间中。如果被强行抹掉，程序启动时动态链接器会直接报 Segmentation fault 或直接拒绝加载。

为什么它运行时必须常驻内存？

因为在现代 Linux 动态链接环境下，你的二进制程序（比如 main）其实是个”半成品”。你调用了 std::cout 或者 printf，但这些函数的真实机器码根本不在你的文件里，而是在系统的动态链接库（比如 libc.so.6、libstdc++.so.6）里。

程序跑起来的第一秒钟，CPU 根本不知道 printf 的物理地址在哪。这时候，系统里的 动态链接器（ld.so） 就会介入：

  1. 动态链接器跑到你的内存里，翻开 .dynsym（动态符号表）
  2. 动态符号表说：”报告长官，我这里有一个外部符号，它的 st_name 偏移量指向 .dynstr 的第 0x0b 个字节“
  3. 动态链接器顺着指针跑到 .dynstr 的 0x0b 位置一读，看到了一个纯文本字符串：**"printf"**
  4. 接着，动态链接器就会拿着 "printf" 这串字符，跑到 libc.so.6 的大仓库里挨个去对暗号。一旦在 libc 里也找到了名字叫 "printf" 的函数，就立刻把它的真实物理地址填进你程序的 GOT（全局偏移表） 盒子里
  5. 最后，你的 CPU 才能顺利跳转，成功打印出东西

在这个过程中，==如果没有 .dynstr 在内存里提供 "printf"、"libc.so.6" 这样的纯文本字符串，动态链接器就会变成”瞎子”，根本无法在线帮你进行函数地址的比对。==

为什么 strip 抹不掉它？

很多工程师为了给二进制文件瘦身，或者为了防止代码被逆向，会执行 strip --strip-all main。

  • 执行之后，.strtab（静态字符串表）会被彻底物理抹去。这时候你用 GDB 连 main 函数都找不到了。
  • 但是，==.dynstr 会完好无损地保留下来。==

因为 strip 工具非常清楚：干掉 .strtab 只是让程序员无法调试，但干掉 .dynstr 就会直接让操作系统无法加载动态链接库，整个程序直接沦为废铁。

==.dynstr 并不是一个”动态函数名表”，它是一个纯粹的 **”动态链接专用字典”**。==

  • .dynsym（动态符号表） 过来查，查到的是函数名、对象名（如 std::cout）
  • .dynamic（动态信息表） 过来查，查到的是依赖的动态库文件名（如 libstdc++.so.6）

.dynstr 与 .strtab 的核心区别：

对比维度 .dynstr（动态字符串表） .strtab（静态字符串表）

==就只有唯一一个硬编码的字符串：/lib64/ld-linux-x86-64.so.2。==这个文件就是 64 位 Linux 系统的标准动态链接器本尊（它是 glibc 的一部分）。

程序启动时的控制权交接流程：

==静态链接的程序没有 .interp 段，因为静态链接的程序不需要 ld.so。==

[1, 2, 39] .note.gnu.property / .note.gnu.build-id / .note.ABI-tag

因为它是结构化的二进制 NOTE 类型数据，直接用普通的 readelf -p（文本打印）只会看到一堆乱码。要完美查看它，在 Linux 终端下用 readelf -n 比较合适。

.note.ABI-tag 规定了运行这个二进制文件的目标系统，其 Linux 内核版本（Kernel Version）的最低门槛。

因为随着 Linux 内核的发展，会不断加入新的系统调用（Syscalls，比如近几年大火的异步 I/O 框架 io_uring，或者新的线程同步锁）。如果你的程序在编译链接时，底层的 glibc 默认开启了某些新版内核才有的高级系统调用，它就会在这个 ABI-tag 里写明：”本程序最低需要 X.X.X 版本的内核支持”。

当用户尝试在一个极度古老的 Linux 服务器上运行你这个程序时，内核在执行 execve 的第一微秒，翻开 .note.ABI-tag 一看：”不好意思，我的内核版本太低，不支持你里面要用的高级系统调用”，==就会直接拒绝加载并安全退出==，防止程序跑着跑着突然调用一个不存在的系统调用而引发不可预知的灾难。

[21] .dynamic：动态链接核心账本

动态链接的整体流程：

  1. 内核加载 ELF，发现其为动态链接 → 启动动态链接器（ld.so）
  2. 动态链接器将 .dynamic 段映射到内存
  3. 遍历 DT_NEEDED 条目，递归加载所有依赖的共享库
  4. 使用 DT_RPATH / DT_RUNPATH（结合 LD_LIBRARY_PATH 等环境变量）搜索库文件
  5. 执行重定位（Relocation）：将库函数的实际内存地址填入 PLT/GOT
  6. 执行 INIT 段 → 跳转 main()

当你在终端按下 ./main 时，Linux 内核只把你的可执行文件加载进内存，而你的代码要调用的 std::cout 或者是 printf 还在外面的 .so 库里。

动态链接器进入内存后的第一件事，就是奔向 .dynamic 节。

  • 它只要看到类型为 (NEEDED) 的标签，就会立刻像接到圣旨一样，跑到硬盘上去把对应的 libstdc++.so.6 或 libc.so.6 加载到进程的内存空间里。
  • ==如果没有 .dynamic 里的这两行记录，动态链接器根本不知道你的程序需要依赖哪些动态库，程序会在第一微秒瘫痪。==

我们在前面讨论过，ELF 里有各种各样的表格：有管动态字符串的 .dynstr，有管动态符号的 .dynsym，还有管地址修正的 .rela.plt（重定位表）。

但是，当程序被加载进内存后，原本文件里的”节区表（Section Header Table）”在很多情况下就失效或者不进内存了。动态链接器在运行时想要找这些表，去哪里找？

==.dynamic 节就是所有这些核心表格在内存中的”永久灯塔”：==

  • 它通过 (STRTAB) 告诉链接器：动态字符串池在内存的 0x528
  • 它通过 (SYMTAB) 告诉链接器：动态符号表在内存的 0x3d8
  • 它通过 (JMPREL) 告诉链接器：函数跳转重定位表在内存的 0x830

链接器在运行期间，只要牵着 .dynamic 这根线，就能在随机化的内存大洋里精准定位到任何一个它想要的底层表格。

.dynamic 的本质：一个由 (Tag, Value/Pointer) 组成的结构体数组。

.dynamic 的地位：==高贵至极，绝对带 A (Alloc) 标志，运行时必须常驻内存。==

.dynamic 与 strip 的对抗：哪怕你执行了最高级别的 strip --strip-all，把 .strtab、.symtab 剁得灰飞烟灭，strip 工具也绝对不敢动 .dynamic 哪怕一个字节。因为动了它，动态链接器就会变成瞎子和聋子，整个程序彻底沦为废铁。

初始化与析构：两代流派

第一流派：传统单点流（INIT / FINI）

  • 0x000000000000000c (INIT) 0x1000
    • 作用：指向一个真正的函数代码入口（对应 .init 节）
    • 内幕：老一辈的初始化方式。它不带大小（SZ），因为动态链接器直接 call 0x1000 强行跳过去执行里面的指令。在现代 GCC 中，它用来打地基，跑一些最基础的 C 运行时（CRT）初始化环境
  • 0x000000000000000d (FINI) 0x1314
    • 作用：传统的散场单点入口（对应 .fini 节）
    • 内幕：对应 INIT，程序彻底退出前，动态链接器会直接 call 0x1314 跑完最后的消亡逻辑

第二流派：现代数组流（INIT_ARRAY / FINI_ARRAY）—— C++ 全局对象催生婆

由于现代程序（特别是 C++）有大量的全局、静态对象和复杂的库初始化，单靠一个 INIT 函数根本装不下。于是现代 ELF 引入了数组（表）的形式：

  • 0x0000000000000019 (INIT_ARRAY) 0x3d70 与 0x000000000000001b (INIT_ARRAYSZ) 16 (bytes)
    • 作用：指向一个函数指针数组（对应 .init_array 节）
    • 内幕：它不是代码，而是账本。INIT_ARRAY 记录了表的首地址（0x3d70），INIT_ARRAYSZ 记录了表的大小（16 字节）。在 64 位系统下，一个指针占 8 字节，16 字节意味着这个数组里精准地装了 2 个函数指针。链接器会用一个 for 循环把这 2 个函数依次调用，你之前看到的 __static_initialization_and_destruction_0（初始化 std::cout 用的）就在这里排队。
  • 0x000000000000001a (FINI_ARRAY) 0x3d80 与 0x000000000000001c (FINI_ARRAYSZ) 8 (bytes)
    • 作用：指向一个析构/清理函数指针数组（对应 .fini_array 节）
    • 内幕：对应 INIT_ARRAY。大小为 8 字节，意味着里面精准装了 1 个清理函数指针（比如通过 __cxa_atexit 注册的析构函数）。

.dynamic 条目的两种数据形态

.dynamic 节里面存放的不仅是地址，它自己就包含了一部分核心元数据。不过，它所指向的那些更庞大的表格（比如字符串、符号表），确实是以独立的 Section 形式躺在 ELF 文件里的。

.dynamic 里的每一行（每一个条目），在内存里其实并不是只有一个孤零零的地址。它是一个由 Tag（类型标签） 和 Value/Address（值或地址） 组成的结构体。

在 C 语言的底层定义中（Elf64_Dyn），每个条目固定占用 16 个字节：

  • 前 8 字节：d_tag（这就是你看到的 0x1、0x19、0x6ffffef5 等数字，它们本身就是元数据，用来告诉系统”我是干嘛的”）
  • 后 8 字节：d_un.d_ptr 或 d_un.d_val（具体的值）

==后 8 字节不一定都是地址！==仔细看你贴出的账本，后 8 字节有两种形态：

  1. 它是指针/地址（Ptr）：比如 (INIT_ARRAY) 0x3d70、(GNU_HASH) 0x3b0。这确实是一个指向文件其他地方的地址。
  2. 它纯粹就是个数字/元数据（Val）：比如 (INIT_ARRAYSZ) 16。这里的 16 根本不是地址，它就是数字（代表数组大小是 16 字节）。还有 (RELAENT) 24，代表每个重定位条目是 24 字节。

各条目详细解读

**(STRSZ) 376 (bytes)**：字符串表（STRTAB）的总长度。告诉链接器：字符串池子一共 376 字节大，超过这个范围就不要去读了。

**(SYMENT) 24 (bytes)**：符号条目的大小。告诉链接器：动态符号表（SYMTAB）里的每一个”函数户口条目”都严格占用 24 字节。链接器遍历符号表时，每次指针往后移动 24 字节（+24）就能稳稳对齐下一个符号。

**(PLTRELSZ) 120 (bytes)**：函数重定位表（JMPREL）的总大小（120 字节）。链接器一算 $120 \div 24 \text{ (每个条目)} = 5$，就知道有 5 个外部函数需要进行符号绑定。

**(RELASZ) 288 (bytes)**：变量重定位表（RELA）的总大小（288 字节）。

**(RELAENT) 24 (bytes)**：变量重定位表（RELA）单个条目大小（24 字节）。两数相除得 12，意味着运行时有 12 个全局变量/指针需要链接器去修正地址。

**(RELACOUNT) 4**：明确告诉链接器：”在重定位表里，前 4 个条目是纯粹的 R_X86_64_RELATIVE（相对地址修正）类型。”链接器看到这个数字后，直接启动底层批量循环，闭着眼睛把这 4 个地址加上程序运行时的基地址，不需要再去大费周章地查符号表名字，极大地加速了启动速度。

**(VERNEEDNUM) 2**：依赖的版本数量。告诉链接器，当前程序对外部库有 2 个强烈的版本依赖要求（比如一个依赖 libc 的某个版本，一个依赖 libstdc++ 的某个版本），链接器需要去校验 2 次。

  • 走向第二个文件 libc.so.6，里面有 2 个 要求：GLIBC_2.34 和 GLIBC_2.2.5

为什么 libc.so.6 一个人就占了两个版本（2.34 和 2.2.5）？

你可能会纳闷：既然有了高版本 GLIBC_2.34，为什么还要大费周章地写一个极其古老的 GLIBC_2.2.5（这甚至是 20 多年前 AMD64 架构刚诞生时的初代 Glibc 版本）？

这是因为 Linux 的 Glibc 为了保证向后兼容性，搞了”符号版本分流”：

  • 你的程序里用了一些二十年来从来没变过的基础函数（比如 printf、malloc），它们在 C 库里依然挂着初版户口 @GLIBC_2.2.5
  • 同时，你的程序里也用了一些现代 Linux 才加入的、或者近期重写过的高级安全/核心函数（比如现代的进程启动初始化函数 __libc_start_main），它们被挂上了新户口 @GLIBC_2.34

**(PLTREL) RELA**：重定位格式声明。告诉链接器：这个程序使用的是现代的 RELA（带显式加数 Addend 的重定位结构），而不是古老的 REL 格式。链接器内部会据此切换解析结构体的代码。

**(FLAGS) BIND_NOW**：==最高级别的安全/性能防御电闸。==

正常情况下，Linux 默认采用”延迟绑定（Lazy Binding）”，即程序启动时不解析外部函数，等你第一次调用 printf 时才去查地址。

开启 BIND_NOW 后，策略直接逆转。链接器在程序冷启动的瞬间，必须立刻、马上把所有外部函数地址全部填好。由于启动时就全填完了，随后系统会把存放地址的 GOT 表彻底锁死为只读（Read-Only），这被称为 Full RELRO 技术。黑客即便发动缓冲区溢出攻击，也无法篡改任何函数指针，直接废掉了黑客的”执行流劫持”卡牌。

**(FLAGS_1) Flags: NOW PIE**：进一步向链接器表明身份。

  • NOW 的作用同上
  • **PIE**：告诉链接器”我是一个位置无关的可执行文件（Position-Independent Executable）”。链接器看到这个标志就知道：这个程序支持 ASLR（内存地址随机化），每次启动时，请把它随机丢到内存的任何空闲角落

**(NULL) 0x0**：==物理边界标志。==它既不是地址，也不是参数，它就是一个 0。动态链接器在用 for 循环一行行读取 .dynamic 数组时，一旦判断 Tag == 0，就立刻跳出循环。如果没有这个 NULL 条目，链接器就会在内存里无限往下读，直到引发内存越界错误。

**(DEBUG) 0x0**：

当你在终端输入 gdb ./main 调试程序时，GDB 面临一个巨大的难题：GDB 怎么知道你的程序在运行时偷偷加载了哪些 .so 动态库？这些动态库被随机加载到了内存的哪个地址？

如果没有人告诉 GDB，GDB 就无法为你加载动态库的调试符号，你就没办法在外部库函数上打断点。

这个问题的解药就是 DEBUG 条目：

  1. 冷启动时：操作系统把你的程序和动态链接器（ld.so）一起拉进内存
  2. 链接器偷梁换柱：动态链接器（ld.so）启动后，第一件事就是扫描 .dynamic 表，找到 DEBUG 这一行，然后强行把后面的 0x0 覆写成链接器自己内部一个叫做 r_debug 的结构体内存地址
  3. GDB 顺藤摸瓜：当 GDB 挂载到你的进程时，它会雷打不动地直奔 .dynamic 的 DEBUG 条目，读取被链接器刚刚填进去的那个神秘地址
  4. 拿到共享库链表：通过这个地址，GDB 就能读到 r_debug 结构体，里面包含了一个双向链表（link_map），这个链表里清清楚楚、实时更新着当前进程加载的每一个 .so 文件名及其在内存中的绝对基地址

0x0 只是一个占位符而已。
